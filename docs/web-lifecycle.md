# Постоянный веб и ручная очистка ресурсов

Штатный Ethernet-веб запускается автоматически при появлении PHY link. Пока
сеть не поднята, main продолжает обслуживать часы и тач. Неудачная попытка
инициализации допускает повторный запуск; успешный сервер работает бессрочно.
У него нет общего таймера остановки/очистки. ESC остаётся диагностическим выходом;
после него автоматический повторный запуск выключен до перезагрузки или явной
команды. Кнопка очистки ESC не посылает и сервер не останавливает.

```sh
python3 scripts/display-control.py --web-run
```

Без числа, или с 0, команда запускает/подключает наблюдение постоянного веба.
Если он уже активен, `net web serve` только сообщает WEB RUN ACTIVE, не меняя
его время жизни. Положительная длительность сохранена для явно запускаемых
ограниченных диагностических сессий из idle; это не штатная политика очистки.
Таймауты зависших отдельных TCP/файловых передач остались, общего TTL кешей нет.

## DHCP

В существующем smoltcp включён `socket-dhcpv4`; новых пакетов/C-зависимостей нет.
DHCP — дополнительный статический SocketStorage в том же сетевом poll, без heap.
Клиент получает адрес, продлевает аренду на T1, делает rebind на T2. Неизменившаяся
конфигурация после ACK не закрывает TCP/файлы. Старое ограничение времени сервера
сроком DHCP-аренды удалено. Если аренда действительно потеряна, IP снимается и
старые TCP-соединения прерываются, но веб-цикл, RTC/тач и готовый аудиокеш продолжают
обслуживаться, пока DHCP получает новый адрес. Это не файловый GC по таймеру.

Хостовый тест с Ethernet-кадрами проверяет discover/offer/request/ack, ARP и renew,
продление за пределы исходной аренды, затем настоящее истечение без ACK.
Первичный DHCP/автозапуск проверены на роутере; многочасовое продление физической
аренды в этом сеансе не ожидали.

## Кнопка «Закрыть файлы и освободить кеши»

Находится в «Управление бордой». `POST /api/resources/release`, пустое тело.
GET и запрос с непустым телом отклоняются. UI предупреждает об отмене передач,
останавливает свою очередь загрузки/сетевой тест и ждёт фактического результата.

Обработчик в одном foreground-владельце:

1. Если будильник активен, возвращает 409. Звучащая мелодия не прерывается.
2. Прерывает текущие файловые TCP-передачи. FileTable закрывает readers/appends
   и abort-ит незавершённые CreateNew с удалением их цепочек. Уже завершённые файлы
   не удаляются; записанный append сохраняется.
3. Выполняет checkpoint/sync и инвалидирует только чистые FAT/read-through линии.
   Dirty/I/O-error, существовавшие при mount, не снимаются: read-only том не
   превращается в якобы исправленный. Ошибки/poison дают 503.
4. Повторно проверяет будильник: если он начался во время длинного освобождения
   цепочек, оставляет аудиокеш и возвращает 409. Файлы к этому моменту уже могут
   быть закрыты; сообщения UI не обещают, что операция вообще не начиналась.
5. Удаляет кеш PCM и кольца upload. Проверяет отсутствие живых leases во внешней
   арене и сбрасывает её курсор. Возвращает 200 JSON только после завершения:

```json
{"freed_bytes":5940736,"psram_used":0,"open_files":0}
```

TCP/DHCP и интерфейс не перезапускаются. Framebuffer, минимальные сетевые буферы,
HTTP scratch и небольшой переиспользуемый PCM workspace остаются. FAT-линии
инвалидируются, их фиксированные SRAM-массивы не выгружаются. `psram_used` относится
к арене данных 28 МиБ, отдельно от резерва дисплея 4 МиБ. Это освобождение памяти,
а не гарантированное стирание физического содержимого.

Ранее Player каждый раз выделял workspace; теперь 2 КиБ SRAM возвращаются
в запасной workspace Network и используются при следующем alarm, без роста
bump-арены при повторных очистках. Аудиокеш после очистки не загружается немедленно:
его загрузит следующий AF. Она занимает время; пока идёт подготовка, UI/TCP
обслуживаются, но файловые запросы ждут общую ФС. Если SATIE.WAV изменили, после
очистки будет прочитан новый файл. Source/frames не выделяются заново на refill.

Инициализация большого кеша вызывает housekeeping после каждых 4 КиБ. Диапазон
и lease резервируются до callbacks, поэтому вложенная аллокация не накладывается
на него, а попытка сброса занятой арены отклоняется. На плате пауза Ui снизилась
с 636,181 до 65,177 мс; оставшаяся однократная задержка включает настройку ES8311
до начала звучания. Во время самого звучания max poll gap был 4,952 мс.

HTTP-слоту очистки временно отключается TCP idle timeout, чтобы длинное удаление
FAT-цепочки не оборвало подтверждение по 30-секундному лимиту. Обычный timeout
восстанавливается после ответа. Клиентское отключение всё равно может лишить
браузер подтверждения; UI в этом случае не заявляет успешную очистку.

## Владение памятью и запас управления

Buffer теперь удерживает счётчик leases своей арены. Drop снимает lease, но сам
по себе не возвращает отдельный участок bump-арены. `reset_if_unused(&self)`
сбрасывает всю арену только при leases=0; живой slice удерживает Buffer, а забытый
Buffer блокирует reset. Эксклюзивный reset тоже проверяет счётчик. Драйвер обязан
удерживать DMA-lease до подтверждённой остановки: счётчик не заменяет владельца
периферии. В очистке нет unsafe-обхода живых Rust-буферов.

TCP-слотов теперь 5, но одновременно допускаются 4 файловые передачи. Это
оставляет дополнительную ёмкость под управление при четырёх занятых файлах;
не является защитой от произвольного числа зависших/враждебных соединений.
Цена дополнительного TCP-буфера — 22 КиБ SRAM. DMA pool peak=131968/139264,
рабочий scratch+PCM workspace peak=10240. FileTable остаётся на 5 handles,
последний нужен в том числе для page/audio metadata work.
