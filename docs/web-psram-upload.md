# HTTP upload через PSRAM — исходный одиночный буфер

Историческое описание первого этапа от 2026-11-14. Текущий приём использует
[PSRAM-кольцо с перекрытием TCP/SD](http-upload-ring.md), а не один блок.

Обычный проводной web-run теперь использует:
TCP RX SRAM → общий scratch SRAM8KiB → очередь файла PSRAM32KiB → SDMMC DMA.
Создание/расширение FAT и сохранение каталога выполняются прежним FAT-слоем.
Это интеграция [прямого TX](sd-psram-dma.md), не обещание его лабораторной
скорости для сетевой загрузки с выделением новой цепочки.

## Память

Пул UploadPool выделяет блок по требованию первого непустого PUT. На активную
загрузку приходится32KiB PSRAM и128B guards. Свободные блоки передаются другим
TCP-слотам и повторно используются; новые выделяются только при росте пика
одновременных загрузок, максимум4. После close/abort блок свободен для повторного
использования, физическое место в bump-арене сохраняется до конца web-run.
Нельзя считать его возвращённым глобальному аллокатору после каждого файла.

Нормальный web-run требует used=0 внешней арены при входе; framebuffer имеет
отдельный резерв и не затрагивается. Арена сбрасывается после остановки и cleanup.
Штатный SD bounce остаётся8KiB, общий HTTP scratch8KiB, без большого SRAM bounce.
Массив дескрипторов расширен до8×64B для прямого запроса32KiB. Нет аллокаций
на каждый пакет или на каждые32KiB записанного файла.

## Данные и владение

Промежуточные TCP-порции кратны512B, накопление идёт до32KiB; последнее тело
может иметь произвольную длину. Последний хвост записывается точной длины:
целые секторы из PSRAM идут напрямую, неполный сектор — через write-through
sector cache и малый SRAM bounce. Пустой файл не получает очередь.

FileTable QUANTUM теперь32KiB. Card backend сообщает максимальный секторный
batch32KiB: прямой PSRAM TX использует его, RX и обычные SRAM/bounce запросы
при необходимости разбиваются на8KiB. Синхронные старые SD-клиенты сохраняют
8-КиБ ограничение; размер их фиксированного буфера не изменён.

Buffer.data() остаётся неизменяемым до завершения await записи. Request::Drop
останавливает DMA перед освобождением прямого источника; неудачная остановка
не позволяет нормальное продолжение. Очередь заполняется заново только после
завершения SD-запроса. Условия D-cache OFF, L2=0, uncached PSRAM сохраняются.
CPU копирует в PSRAM упакованными словами, с fence/паузой320тактов каждые64B —
по прежней политике совместной работы CPU-записей и LCD. Это имеет стоимость.

Недополученное тело/обрыв соединения приводит к abort CreateNew и удалению
созданной цепочки. Накопленные32KiB в PSRAM не считаются сохранёнными на карте.
Ответ201 выдаётся после полного тела, close и checkpoint; до этого отключение
питания может потерять очередь и оставить том dirty как раньше.

Optional Wi-Fi не получает внешнюю арену и сохраняет старый scratch/bounce путь.
Это не его аппаратный тест. Большие диагностические 32-КиБ SRAM statics остаются
только в sd-wide-bench; для обычной загрузки они не нужны.

## Диагностика

WEB READY содержит staging=PSRAM32K. WEB UPLOAD DONE печатает размер, количество
flushes и полное время запроса. Каждые64MiB есть WEB UPLOAD PROGRESS.
SD WRITE TOTALS — накопительные счётчики завершённых прямых байт/запросов и
байт через bounce за всю web-сессию (при параллельных клиентах общие).
WEB STAGING на выходе сообщает число выделенных блоков и peak_active.

Для1GiB без хвоста ожидается32768 порций по32KiB. Это число пользовательских
flushes; реальные запросы также включают FAT и могут дробиться по кластерам.

## Проверки

Host88 tests, Clippy default, сборка diagnostics+wifi+software-jpeg,
host-тесты sd-wide-bench. Пул проверяется на ленивое выделение, повторное
использование между TCP-слотами, независимость двух очередей, невыровненные
хвосты и отказ при выходе за границы. Предыдущие failure/cancellation тесты
секторного кеша сохранены.

На плате:0,1,511,512,513,32767,32768,32769,65539B; два одновременных PUT
по2MiB+15/7; каждый файл прочитан и сравнен полностью. Намеренно оборван
PUT50000B после40000B (уже один полный32-КиБ блок на карте): файл удалён,
очередь пригодна к дальнейшей работе. Исходный root неизменен.

HTTP8MiB: PUT6,016s=1,33MiB/s, GET2,167s=3,69MiB/s;256 flushes.
Прироста end-to-end относительно предыдущих коротких тестов пока не доказано:
TCP/CPU→PSRAM, pacing, FAT и задержки карты остаются в общем времени.
Лабораторные14,8MiB/s прямой перезаписи не являются скоростью HTTP upload.

Логи/скрипты: target/storage-profile/p4-upload-*.

64MiB через HTTP: PUT51,934s=1,232MiB/s, GET17,220s=3,717MiB/s.
2048 flushes; разность SD WRITE TOTALS составила ровно67108864 прямых байта
и2048 прямых запроса. Полное сравнение/SHA прошло, временный файл удалён,
исходный root сохранён. Это проверяет реальную работу прямого пути при записи
нового файла; быстрее предыдущего веб-пути он пока не стал.

После остановки тестовой web-сессии: external used=0, peak65792B (два блока
по32896B); DMA used=0, peak117632B; working SRAM188480B; стек52768/65536B,
guard_ok=true. Затем веб снова запущен для пользовательского1GiB теста.

Пользовательская большая загрузка2026-11-14 завершилась:776394502B
(740,427MiB),550,249s (9мин10с), средняя1,346MiB/s.23694 flushes, последний
хвост22278B. WEB UPLOAD DONE и HTTP HEAD200/Content-Length776394502
