# Почему запись SD отстаёт от Linux — 2026-11-13

Сохранённая исходная точка: `1778e2e`. Предыдущие измерения —
[storage-write-profile.md](storage-write-profile.md).

## Что сравнивали

Linux в USB-ридере записал 2 ГиБ блоками по 4 МиБ через O_DIRECT с финальным
fsync: 21,75 МиБ/с. Начальный burst был выше; это не одна неизменная скорость.
P4 использовал транзакции максимум по 8 КиБ, а FAT дополнительно записывала
секторы по 512 Б. Поэтому прежнее сравнение не изолировало интерфейс карты.
Reader также использует другой скоростной режим, чем Native SD на плате.

Диагностический файловый тест теперь после создания файла оставляет его
CreateNew handle открытым, выполняет sync, затем seek(0) и перезаписывает
уже выделенную цепочку разными порциями. Каждый проход включает sync.
Размер файла — 8 МиБ. После последнего прохода всё содержимое проверяется
чтением; файл удаляется. Чужие файлы и свободные сектора напрямую не пишутся.
Это файловая перезапись, не raw-device benchmark. Проверка чтением выполняется
после последнего прохода, не после каждого промежуточного прохода.

## Размер транзакции оказался главным фактором

CPU 160 МГц, I-cache ON, D-cache OFF, L2=0, PSRAM uncached, LCD активен.
В одном образе sd-wide-bench после оптимизации копирования:

| Порция перезаписи | Время 8 МиБ | МиБ/с |
| --- | ---: | ---: |
| 512 Б | 36,769 с | 0,218 |
| 2 КиБ | 9,075 с | 0,882 |
| 8 КиБ | 2,530 с | 3,162 |
| 32 КиБ | 0,778 с | 10,284 |

Создание нового файла по 32 КиБ: 2,033 с, 3,934 МиБ/с.
Разница с перезаписью — прежде всего выделение цепочки FAT. На создание
пришлось 1073 секторные записи метаданных против 256 записей данных.
Время запросов метаданных 1,140 с, данных 0,769 с (без верхнего слоя).

В предыдущем 32-КиБ образе до ускорения копирования перезапись занимала
1,035 с (7,730 МиБ/с), 8-КиБ порциями — 2,568 с (3,115 МиБ/с).
Увеличение порции уменьшило ready_us с 1,265 с до 0,262 с, CMD13 с 2574 до 519.

После ускорения копирования 32-КиБ проход дал setup=110439 us,
data=385458 us, stop=2173 us, ready=258885 us. В data входит наблюдение
завершения DMA, а не только передача на проводах; setup включает копирование,
настройку дескрипторов, кеш-операции и reset. Называть весь setup чистым memcpy
некорректно. Верхний слой добавил около 22 мс к сумме SD-запросов.

## Что исправлено в обычном образе

1. Секторный кеш Stream имеет две строки вместо одной; данные write-through.
   Запись большого диапазона инвалидирует только пересекающиеся строки до
   начала I/O, включая ошибки и отмену. Несвязанные FAT-строки сохраняются.
   При создании 8 МиБ чтения SD сократились с 1042 до 32; записи не откладываются.
   Цена — примерно 0,5 КиБ на Stream и дополнительный код.
2. Заполнение DMA bounce buffer использует выровненные u32-загрузки, если
   адрес источника кратен четырём. Для остальных срезов сохранён байтовый путь.
   Проверены все четыре смещения источника; в дизассемблере выровненный цикл
   содержит lw/sw, невыровненный — lbu и сборку слова.

Ускоренное копирование есть в синхронном и async путях. В обычном образе
максимальная транзакция остаётся 8 КиБ. HTTP RX 6 КиБ не превращается
автоматически в 32-КиБ записи от изменения драйвера.

## Отдельный экспериментальный образ

`./scripts/image.sh --features sd-wide-bench`, затем обычная прошивка
firmware.bin и `scripts/display-control.py --sd-files-bench 8`.
Профиль включает diagnostics и поднимает SD MAX_TRANSFER / FileTable QUANTUM
до 32 КиБ. 32-КиБ bounce buffer и 32-КиБ входной scratch находятся в верхней
SRAM (.bss); 8-КиБ boot stack и DMA-пул Ethernet не используются под них.
Это временный расход SRAM для эксперимента. Применять профиль отдельно;
сочетания с Wi-Fi/L2-профилями не проверялись. На плату после измерений
возвращается обычный образ с 8-КиБ транзакциями.

## Что исключили и чего ещё не доказали

Удаление задержки до следующего CMD13 увеличило число CMD13 с 5339 до 143170,
но время создания осталось около 4,3 с. Этот вариант откатан: пользы не было,
а служебных команд стало намного больше. Таймауты/проверки READY не снимались.

Время ready включает задержку опроса и обслуживания, поэтому оно не является
прямым измерением времени программирования NAND. Отдельные прогоны 8-КиБ
перезаписи дали 2,8–4,7 с: карта/её внутреннее состояние существенно влияют
на короткие тесты. Кеш двух секторов достоверно убирает чтения, но не даёт
основания обещать одинаковое ускорение end-to-end: HTTP после его добавления
без word-copy дал 1,00 МиБ/с против прежних 1,15 МиБ/с в другом прогоне.

10,28 МиБ/с — результат короткой перезаписи без сети, не sustained-гарантия,
не скорость создания нового файла и не результат веб-загрузки.

## Следующий шаг для обычного веб-пути

Нужен управляемый накопитель входящих данных и более крупные SD-запросы:
получать небольшие TCP-порции, собирать хотя бы 32 КиБ, писать карту одним
запросом. Буфер должен выделяться на активного writer, освобождаться при
close/abort и учитывать несколько файлов и задержки обслуживания аудио.
Простое увеличение TCP RX или постоянных буферов каждого слота не требуется.
Отдельно стоит объединять мелкие обновления FAT, с явными барьерами dirty,
sync и публикации directory entry. Write-back без этих правил не добавляли.

Локальные логи: target/storage-profile/{p4-rewrite,p4-cache,p4-wide,p4-word}-*.

## Финальная проверка обычного образа

После возврата default (8-КиБ SD, без diagnostics/Wi-Fi/software JPEG):
HTTP PUT 8 МиБ — 5,767 с, 1,387 МиБ/с; GET — 2,171 с, 3,684 МиБ/с.
SHA и содержимое совпали, тестовый файл удалён, root остался прежним.
Сравнивать один этот прогон с прежними 1,15 МиБ/с как стабильный процент
ускорения нельзя из-за наблюдаемого разброса карты.

Прошли 86 host-тестов в core и 86 в sd-wide-bench, Clippy обоих профилей,
release-сборка diagnostics+wifi+software-jpeg и повторная проверка HTTP reconnect,
трёх параллельных клиентов, RST, неполного тела и SD read/write.
Payload default: 262064 Б. Веб после теста оставлен на Ethernet.

Следующий эксперимент подтвердил прямой SD DMA из PSRAM с равной SRAM скоростью; текущий sd-wide-bench выполняет матрицу источников, все порции 32 КиБ: [sd-psram-dma.md](sd-psram-dma.md).
