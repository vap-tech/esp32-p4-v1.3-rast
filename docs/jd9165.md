# JD9165: возможности и план графического тракта

Исследовано 2026-11-04. Обновление 2026-11-05: публичные функции и аппаратные
пробы описаны в [display-api.md](display-api.md). Основной текст — анализ документации; подтверждённый на плате
режим остаётся BER, 2×550 Mbps, RGB565, подсветка 5% на 20 кГц.
Результаты аппаратных испытаний: [display.md](display.md).

BA-DS и A-A не считать одной подтверждённой ревизией: полного register manual
BA-DS не найдено. На физическом экземпляре маркировка не прочитана, DCS ID
возвращает 00 00 00. Сильное косвенное подтверждение: **все 48 непустых
vendor-команд побайтно совпадают** с первыми 48 командами нашего INIT.
Последние две — sleep out/display on: в vendor init без параметров, у нас
исторически с нулевым параметром плюс дополнительный DISPON без параметров.

## Что следует из описания контроллера

JD9165, стр.4–5, 24: **полного framebuffer/GRAM нет**, есть строчный тракт;
OTP хранит настройки. Документированных примитивов рисования нет. Нужен
непрерывный видеопоток; загрузка только изменённых прямоугольников в панель
не заменяет обновление кадра. BIST панели выдаёт заливки, градации, шахматную
сетку, рамку без видеовхода. Это отдельный генератор, не VPG ESP32-P4.

A-A, стр.26–32, 37, 44–65, 67–71:

| Возможность | Ограничение |
|---|---|
| RGB565/666/888 | VPG проверен в RGB565/RGB888; RGB666 отдельно не реализован |
| Burst / non-burst video | Тайминги и LP-интервалы обязательны |
| 2 lanes: до 750 Mbps/lane | Предел A-A; BA-DS и наша разводка отдельно не проверены на максимуме |
| MADCTL: зеркалирование, RGB/BGR | Обмена осей для 90° не описано |
| Sleep, display off, inversion, idle | Idle сокращает число цветов; 1bpp упомянут, полный протокол не раскрыт |
| TE и scanline | Вывод TE на нашей плате не подтверждён |
| DCS 05h: ошибки DSI | 7-битный счётчик + overflow; чтение очищает; не численный BER |
| 06/07/08h, 0Fh | Первый пиксель RGB и self-diagnostic; применимость проверить на BA |

A-A preliminary содержит неточности: 0Ah задаёт D3=1, наш ответ 14h имеет
D3=0; таблицы 09h/36h расходятся в обозначении RGB/BGR. Поэтому универсальные
DCS шаблоны и отдельные биты требуют проверки, особенно на BA-DS.

## Тайминги нашей панели

Vendor init задаёт 2 lanes (`page1:0B=11`), программный выбор lanes
(`page1:20=04`), HS settle (`page1:1F=05`); gamma/GOA/VCOM совпадают с нашей
таблицей. Менять эти настройки ради скорости без дополнительных оснований не нужно.

| Параметр | Текущий тест VPG | Vendor init |
|---|---:|---:|
| Размер | 1024×600 | 1024×600 |
| HSW / HBP / HFP | 20 / 136 / 160 | 24 / 136 / 160 |
| VSW / VBP / VFP | 2 / 12 / 20 | 2 / 21 / 12 |
| Htotal / Vtotal | 1340 / 634 | 1344 / 635 |
| Ожидаемый pixel clock, MHz | 50 | 51.2 |
| Расчёт fps | ~58.85 | ~59.9925 |

Текущий host округляет HLINE до 1843 byte clocks; отсюда VPG ~58.838 Hz.
Реальная частота кадров внешне не измерялась.

В модульном PDF, стр.8: таблицы **при 60 Hz**, DCLK DE 40.8…67.2 MHz,
HV 44.9…63 MHz, типичный 51.2 MHz. Это диапазоны в сочетании с разными
blanking/total, **не разрешение получить 80–100 Hz при прежних porch**.
Обозначение back porch в таблице может включать sync; vendor init и SDK
задают sync отдельно. Поэтому переносить столбцы напрямую нельзя.

Перед реальным DPI нужно настроить и bridge: сейчас VPG обходит его пиксели.
У SDK ожидаемые 50 MHz при PLL240/div5 дают реальные 48 MHz; bridge Htotal
компенсируется, host HLINE считается по ожидаемой частоте. На rev1.x следует
согласовать оба домена по локальному `mipi_dsi_hal.c`, а не просто подключить DMA
к сегодняшнему VPG. APLL можно рассмотреть отдельно; он ещё не поднят.

## Наш расчёт ресурсов, а не обещание производительности

Активные пиксели при 60 Hz, без DSI overhead и blanking:

| Формат | Один полный буфер | Два полных буфера | Чтение дисплеем |
|---|---:|---:|---:|
| RGB565 | 1 228 800 B | 2 457 600 B | 73.728 MB/s |
| RGB888 | 1 843 200 B | 3 686 400 B | 110.592 MB/s |

2×550 Mbps дают 137.5 MB/s сырой суммарной линии; это не полезная скорость
приложения. Для RGB888 нельзя судить по одной средней скорости кадра:
важны время пакета строки, HS/LP-переходы, header/CRC и porch.
Пример оценки пиксельного интервала: `51.2 MHz * 24 / 2 = 614.4 Mbps/lane`
ещё до overhead. Поэтому смену RGB565→888 надо сопровождать расчётом
и испытанием lane rate, а не обещать прежние 550 Mbps.

Рендеринг добавляет записи/чтения памяти поверх scanout. Полная перерисовка
RGB565 на 60 Hz — ещё 73.728 MB/s записей; смешивание слоёв добавляет чтения.
Экономия от dirty rectangles относится к renderer, scanout остаётся полным.
Синхронизация кеша и владение DMA-буфером понадобятся при подключении PSRAM.

## Как выжимать возможности на ESP32-P4

Это план framebuffer/renderer; эти части пока не добавлены. Команды панели,
LP/BTA и тестовые видеорежимы уже реализованы: [display-api.md](display-api.md).

1. Поднять PSRAM и надёжный scanout RGB565: DMA → DSI bridge → host → панель.
   Начать с одного буфера; затем двойная буферизация и смена на границе кадра.
   На rev1.x у bridge нет поддерживаемого SDK VSYNC event, поэтому способ
   безопасной смены нужно отдельно проверить через DMA/frame boundary.
2. Разделить renderer и scanout. Рисовать линии/кривые/текст/изображения в буфер;
   менять только нужные области. Для векторов использовать CPU-растеризацию,
   позже ускорять подходящие операции аппаратно.
3. PPA P4 выполняет fill, alpha blending, scale/rotate/mirror — это ускорение
   операций над растрами. [Документация PPA](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32p4/api-reference/peripherals/ppa.html).
   Поднять свой ограниченный HAL для ревизии 1.3; готовый SDK не подключать.
   DMA2D рассмотреть для копирования прямоугольников; не путать с DMA scanout.
4. Если нужна экономия памяти, рендерить строки/полосы в два небольших SRAM
   буфера и отдавать DMA по очереди. Два буфера по 16 строк RGB565 — 65536 B;
   при 60 Hz полный период строки ~26.25 us, 16 строк ~420 us. Это ориентир,
   реальный deadline зависит от DMA/FIFO. Нужно успевать с запасом и без USB-блокировок.
   Наша текущая DATA-область всего 32 KiB: сначала изменить карту памяти.
5. Для качества градиентов — испытать RGB888. Для скорости UI — сперва
   профилировать renderer/PSRAM/DMA, затем настраивать тайминги. Частота линии
   и частота кадров — независимые настройки.
6. Для проверки сигнала — VPG P4 и счётчик ошибок приёмника, для проверки
   матрицы — BIST JD9165. LP/BTA в vertical blanking и чтение счётчика уже проверены. Чтение счётчика
   не является пассивным. Программный BIST BA пока не предоставляется.

[DSI API Espressif](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32p4/api-reference/peripherals/lcd/dsi_lcd.html)
и локальные `esp_lcd_panel_dpi.c`, `mipi_dsi_hal.c`, `mipi_dsi_brg_ll.h`
использованы как справочник по аппаратному пути, не как зависимость проекта.
