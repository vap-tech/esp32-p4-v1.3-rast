# Несколько файлов и порционное обслуживание HTTP

`storage::files::FileTable<'v, 'io, D, const N: usize>` эксклюзивно владеет томом
через borrow на время работы. Вместимость задаётся при сборке; файловый интерфейс
не зависит от N. Веб сейчас использует N=5, TCP-соединений четыре. Это отдельные
лимиты; число общих буферов также не обязано совпадать с ними.

## Память и владение

На ESP32-P4 таблица пяти файлов занимает **4408 B**. Если открыты три файла,
два слота свободны, но небольшой резерв под их метаданные остаётся. Данных,
отдельного sector cache или 8-KiB массива в каждом слоте нет. На все передачи
один shared scratch 8 KiB и прежний SD DMA bounce 8 KiB. Проводной веб дополнительно
накапливает upload в PSRAM по 32 KiB: пул выделяется лениво, переиспользует
освободившиеся блоки между TCP-слотами и хранит максимум достигнутой одновременности
(до четырёх очередей). Арена очередей освобождается при выходе из web-run.
На очередь добавлены два guard по64 B. Heap/RTOS не добавлены.

`FileHandle` — закрытые поля slot + generation. Generation выдаётся глобально
для каждой успешной попытки выделения; старый дескриптор не принимается после
закрытия, переиспользования slot или создания новой таблицы. При исчерпании
счётчик не оборачивается: GenerationExhausted. Неверный handle возвращает
InvalidHandle; заполненная таблица — TooManyOpenFiles без создания файла.

Backend context скрыт в slot. Он содержит курсор, текущее положение в цепочке
кластеров и dirty directory entry. Это не self-referential объект и не открытие
по полному пути на каждый блок. FAT работает через vendored suspend/resume API;
приватность контекстов и единственный владелец тома обеспечивают его инварианты.
Все операции выполняются последовательно с коротким &mut borrow таблицы.

Несколько читателей одного файла разрешены; писатель эксклюзивен по отношению
к другим писателям и читателям. Проверяется физическая directory-entry identity:
регистр, LFN/SFN и aliases родительских папок не обходят блокировку. Remove/rename
открытого файла или его предка возвращают Busy; операции с другими файлами
разрешены. Перемещение папки в своего потомка отклоняется. Atime не обновляется.

## API

Режимы: Read, CreateNew (без перезаписи), Append (открыть или создать).
`info` возвращает длину, позицию, режим. `read`/`write` обслуживают **до 32768 B**
за вызов и возвращают фактическое количество; caller обрабатывает остаток.
У каждого файла свой курсор. `seek` не расширяет файл и запрещён для Append.
Append выбирает EOF внутри сериализованной операции; небольшая запись не может
перемешаться с другой операцией. Open/seek большого файла могут обходить цепочку
кластеров — это ещё не жёсткий realtime budget на любой метод.

```rust,ignore
let mut files = FileTable::<_, 5>::new(&mut volume);
let image = files.open("/photo.jpg", OpenMode::CreateNew).await?;
let log = files.open("/temperature.log", OpenMode::Append).await?;
files.write(image, &jpeg_chunk).await?; // обработать возвращённое число байт
files.write(log, b"23.5\n").await?;
files.sync(log).await?;
files.close(image).await?;
files.close(log).await?;
```

Запись данных и sync разделены. `sync(handle)` сохраняет его directory entry и
FSInfo, вызывает stream flush, сохраняя dirty тома при открытых писателях.
`close` сохраняет писателя и освобождает slot. Только завершение последнего
писателя позволяет пометить том clean. SD write всё ещё ждёт card-ready;
гарантии отключения питания для внутреннего кеша карты не добавлены.

`abort` удаляет только CreateNew. Сначала сохраняется first cluster, затем
удаляется вся цепочка; незаписанный directory entry не должен терять кластеры.
Для Append откат не обещается: close сохраняет уже дописанное. `shutdown` удаляет
незавершённые create и закрывает остальные файлы. Drop таблицы с писателями,
ошибка или отмена I/O оставляют poisoned/dirty; новые записи блокируются.
Автоматического fsck/журнала/отката после power loss нет.

## Веб

GET/HEAD/PUT стали отдельными bounded transfer states. Round-robin чередует
одну порцию каждого активного файла; при полном TX или пустом RX файл уступает
место остальным. Между SD транзакциями обслуживается сеть. Read-ahead сверх
доступного TCP TX capacity не выполняется; собственных больших pending buffers нет.

Зависший клиент ограничен 30 s без прогресса. Обрыв PUT удаляет только его
незавершённый файл. ESC завершает текущую bounded SD-операцию, затем делает
shutdown всех handles; не отменяет DMA посередине штатной остановки.
Файл CreateNew может быть виден в listing до close с ещё не сохранённой длиной;
скачать его до закрытия писателя нельзя (Busy). Это не atomic publish.

Файловые GET/PUT действительно чередуются. Остальные небольшие HTTP endpoints,
включая listing/Flash page/control и RAM speed test, пока остаются синхронными
кооперативными обработчиками. Браузерная очередь загрузок всё ещё последовательная;
параллельные файлы проверены отдельными клиентами. Обновление часов не добавлено.

Температурный датчик и panic/IRQ logger пока не подключены к сервису. API Append
есть, тесты чередуют два лога с картинками; для IRQ требуется отдельная bounded
очередь сообщений, а не файловый вызов прямо из обработчика. Здесь нет скрытого
общего mutex/executor или автоматически запущенной фоновой задачи.

## Сборка и проверки

Для сохранения SRAM release runtime теперь opt-level=z, smoltcp отдельно=s.
Не уменьшаются стек, буферы или минимальная guard рабочей арены. Карта памяти
сохраняет L2=0, uncached PSRAM, D-cache OFF; I-cache включает проводной web-run.
Историческая полная сборка до разделения features: payload около363 KiB, свободная верхняя арена около80 KiB; точные величины
печатаются в memory layout. Пять slot metadata располагаются в runtime stack.

Host90 tests: пять файлов, два изображения + два append logs + read, независимые
читатели/seek, stale/cross-table handle, capacity=1/5, table-full без создания,
alias locks, unrelated remove/rename, directory ancestry, dirty при других
писателях, отмена и чистый remount. Экспорт multifile-fat32.img отдельно прошёл
fsck.fat -n без потерянных цепочек. Frontend и image packer tests прошли.

Плата: GET8MiB держится открытым с остановленным чтением, два PUT512KiB+13/27
завершаются до продолжения GET; четвёртый клиент обрывает PUT. SHA256/содержимое
совпали, aborted file удалён, исходный root unchanged. После suspend/resume
PUT завершились за2.24/2.32s, GET за4.37s с включённой искусственной паузой;
это проверка чередования, не чистый benchmark пропускной способности.

Штатный ESC с двумя активными PUT завершился Ok: после remount оба тестовых
файла отсутствуют, root совпал. Пик стека52868/65536B, guard intact.
В стресс-сессии аппаратный RX missed-frame counter=45 при rx_errors=0:
потери из-за временной нехватки RX descriptors ещё возможны и требуют отдельного
профиля. Проверка данных прошла; это не заявление об отсутствии TCP retries.

Финальная mixed-profile сборка:payload371732B,work82368B. RAM4MiB GET4.927MiB/s,
POST5.304MiB/s;SD1MiB PUT0.635MiB/s,GET3.434MiB/s,данные совпали,файл удалён.
Эти1MiB/4MiB измерения не равны прежнему64MiB sustained benchmark; следующее
исследование скорости SD записи остаётся отдельной задачей.

HTTP upload собирает промежуточные порции кратно 512 Б; последний хвост допускает произвольную длину. Замеры: [storage-write-profile.md](storage-write-profile.md).

Stream держит две строки секторного write-through кеша; записи на карту по-прежнему немедленные. QUANTUM=32 КиБ теперь применяется в обычной сборке. Малый SRAM bounce остаётся8 КиБ; большой прямой TX имеет отдельный лимит и цепочку дескрипторов.

Актуальная интеграция PSRAM upload: [web-psram-upload.md](web-psram-upload.md).

Текущая политика: FAT при записи обычного файла объединяется в отдельном четырёхсекторном кеше, остальные метаданные остаются write-through. [Барьеры и ошибки](fat-writeback.md).
