CPU записывает картинку в PSRAM, а DMA одновременно читает её оттуда для дисплея. Они используют общий путь к этой памяти.
У дисплея есть небольшой запас уже прочитанных пикселей — FIFO. Он позволяет переживать короткие задержки. Но экран выводит пиксели непрерывно: если запас закончился, ждать следующую порцию он не может.
Когда мы рисовали кнопку или индикатор, CPU выдавал плотную очередь записей в PSRAM. Судя по измерениям, DMA временами не получал данные достаточно быстро. FIFO пустел, контроллер фиксировал underrun, а ты видел белую вспышку.
Это не блокировка прямоугольника памяти программным замком. Конкурировали обращения к общей памяти и её контроллеру. Точный внутренний механизм арбитража мы не измеряли, но связь с рисованием подтвердили: во время обновления UI ошибки появлялись, во время записи SD — нет.
Исправили двумя шагами:
Стали писать два пикселя одной 32-битной операцией вместо двух отдельных 16-битных.
После каждых 32 пикселей завершаем выданные записи и делаем паузу примерно 2 микросекунды. CPU в этот момент не пишет, а DMA продолжает работать и может пополнить FIFO.
То есть мы слегка притормозили рисующего, чтобы он не мешал тому, кому данные нужны строго вовремя. Буфер остался один, памяти больше не выделяли.
