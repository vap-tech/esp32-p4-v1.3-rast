# Фоторамка из веба

Запуск только по явному HTTP POST: автоматического старта и настройки через
serial-команду нет. В файловой панели перейти в папку, нажать **Фоторамка**,
выбрать интервал, время работы и эффекты. Папка фиксируется при открытии окна.
Пустая длительность означает работу до остановки; максимум — 24 часа.
Интервал2..3600 секунд отсчитывается после завершения показа/перехода.
Остановка доступна из любой папки и после перезагрузки страницы браузера.
После перезагрузки самой платы начинается обычный IDLE с часами.

В фоторамке часы скрыты, RTC и тач продолжают опрашиваться. Будильник имеет
приоритет: прекращает фоторамку и возвращает зелёный экран с часами и STOP.
Остановка фоторамки не подтверждает будильник. STOP по-прежнему снимает AF
в RTC, сохраняя AIE и возможность следующего срабатывания.

## Показ и ограничения

Baseline JPEG → аппаратный JPEG/full-range RGB565 → аппаратный PPA SRM →
готовый кадр в uncached PSRAM → построчный перенос в постоянный framebuffer.
CPU копирует32-битными словами, делает паузы после64байт записи и обслуживает
сеть/RTC/аудио между группами строк. Чтение трёх точек каждой записанной строки
и защитные границы framebuffer проверяются. Во время подготовки дисплей
продолжает читать предыдущий кадр.

**Бесшовного переключения буферов пока нет.** Проба отдельного кадра/LLI
DW-GDMA не дала ожидаемого completion и вызвала синий экран. Все изменения
DSI/IRQ из опыта убраны: рабочий scanout остался прежним с auto reload.
Перенос готового фото занимает около0,38с, поэтому видна полоса обновления.
Аппаратные JPEG/SRM и их строгий контроль RID/response errors сохранены;
BLEND не вызывается и его RID не маскируется.

При возврате в IDLE зелёный фон тоже записывается построчно с паузами и
обслуживанием I2S. Прежняя сплошная CPU-заливка во время scanout оставляла
underrun latch; после замены остановка по таймеру дала underrun=0.

Эффекты:

- зеркальное отражение — аппаратный SRM;
- поворот каждого второго фото на180° — аппаратный SRM;
- раскрытие слева направо и сдвиг — CPU, шесть дискретных стадий;
- если выбраны оба перехода, они чередуются. Они пока не плавные60fps-анимации.

Вписывание/заполнение используют масштаб SRM с шагом1/16, с центрированием
и чётным выравниванием RGB565. Возможны небольшие дополнительные поля из-за
квантования масштаба. Fill обрезает центральную область, не растягивая её
разными коэффициентами по осям. EXIF-ориентация на плате пока не применяется.

Поддержка JPEG соответствует HAL: baseline Huffman, 8-bit DQT,
gray/YCbCr444/422/420, размеры кратны8. Progressive, CMYK, multiscan и слишком
большие файлы пропускаются. Gray аппаратно декодируется в L8 и расширяется
в RGB565 перед SRM; путь gray16 fixture проверен на плате, в том числе одновременно с HTTP PUT/GET.
Ограничения сервиса: сжатый файл≤2МиБ, декодированный RGB565≤8МиБ,
до64 JPEG в одной папке. Подпапки не обходятся. Порядок — перечисление FAT,
снимок имён делается при запуске. Удалённые/занятые/битые файлы пропускаются;
если подряд не удалось показать ни один файл, режим останавливается.

## Память и файловые операции

Нет новых зависимостей или heap. Нормальная feature `photoframe` включает
`hardware-jpeg`/`hardware-ppa`; диагностические команды остаются отдельными
`jpeg-lab`/`ppa-lab`. Фоторамку можно исключить через `--no-default-features`.

Рабочая область PSRAM выделяется лениво, затем повторно используется: таблица
имён,2МиБ входа,8МиБ декодирования, четыре кадраRGB565 и canaries — около14,8МиБ.
Дескрипторы занимают256байт отдельной внутренней SRAM. При остановке кеш
сохраняется для следующего запуска. Кнопка освобождения ресурсов останавливает
показ, закрывает файлы и освобождает PSRAM; SRAM-дескрипторы сохраняются для
повторного использования, чтобы bump-арена не росла при каждом release/start.

SD принадлежит существующему async FileTable, второго mount/контроллера нет.
Файл открывается на время подготовки кадра и обязательно закрывается, включая
ошибки формата. Четыре HTTP file transfers оставляют пятый слот для медиа.
Операции с ФС сериализованы, сеть и фоновые службы обслуживаются кооперативно.
Аппаратные JPEG/SRM пока блокирующие и ограничены HAL timeout.

## Набор фотографий

На SD: `/PHOTOS/100D3100/DSC_0001.JPG` … `DSC_0010.JPG` — уменьшенные копии;
оригиналы4608×3072 лежат в `ORIGINAL`. Показ запускать из родительской папки.
Оригиналы на ноутбуке не изменялись. Все20файлов прочитаны обратно с SD и
сверены по SHA256.

```sh
python3 scripts/prepare-photos.py /home/kot/Downloads/100D3100
```

Инструмент требует ImageMagick на ноутбуке: auto-orient, предел1536пикселя
по длинной стороне, padding до кратных8, baseline420/quality90, без EXIF.
Create-new, без перезаписи: существующий файл допускается только при совпадении
полного readback SHA256. Большие оригиналы требуют будущего уменьшения
в процессе декодирования/потокового JPEG, текущая версия их не обещает.

## API

| Метод | URL | Действие |
|---|---|---|
| GET | `/api/photoframe` | Состояние: running,folder,file,count,shown,skipped,message,settings |
| POST | `/api/photoframe/start?path=ENCODED&options=10,0,0,0` | Запуск |
| POST | `/api/photoframe/stop` | Идемпотентная остановка; будильник не снимает |

Options: `interval_seconds,total_seconds,fill,effects`. Total0=постоянно,
fill0=вписать,1=обрезка. Effects bits:1 mirror,2 alternate180,4 wipe,8 slide.
Тело запроса не используется и должно быть пустым. GET не запускает и не
останавливает показ. Невалидная настройка, активный будильник, уже запущенный
режим, пустая/недоступная папка —409 с JSON error. Без feature —501.

## Проверки

Host: парсинг ограниченных настроек, допустимая геометрия для альбомных,
портретных и узких изображений, HTTP методы/кодирование путей. Browser VM:
сохранение выбранной папки, флаги эффектов, длительность, остановка и ошибка
старта без ложного подтверждения. Прежние файловые/сетевые тесты сохранены.

На плате: полный круг10фотографий и повтор,12кадров без пропусков; ручная
остановка, таймер, комбинация эффектов/Fill, пустая папка и битый JPEG,
невалидные настройки/методы, release с `psram_used=0,open_files=0`. После
подготовки кадров LCD underrun=0; после paced возврата в IDLE также0.
Обычный показ достигал около58КиБ/64КиБ, guard цел. Дополнительный gray+HTTP
прогон поднял watermark до64356B/65536B, поэтому резерв увеличен до80КиБ
за счёт16КиБ рабочей SRAM; контрольная зона сохранена. Полоса записи —
известное ограничение; визуальную проверку цвета/переходов делает пользователь.

Будильник проверен на штатном ежедневном сравнении16:32UTC/19:32MSK,
без изменения его настроек. Он прервал показ после33кадров без пропусков.
Пользователь нажал STOP: AF=false,AIE=true. Audio:506refill,min_owned=3,
max_poll_gap=31,481мс,max_refill=806мкс,errors=0,underruns=0,guards=true.
Возврат в IDLE дал LCD underrun=0. Лог `target/photoframe-idle-alarm.log`.

Финальная сборка с80КиБ стека повторно прошла gray16→RGB565→SRM,
параллельный PUT/GET1МиБ с SHA256 и3цикла start/deadline/release.
Watermark64464/81920B,guard=true (около17КиБ запаса), LCD underrun=0;
каждый release вернул `psram_used=0,open_files=0`, uptime не сбрасывался.
127host tests,5packer tests, normal/minimal Clippy и combined JPEG/PPA lab build
прошли. История папки при F5 исправлена: `/?path=...`, `/index.html?path=...`
и запасной `/flash?path=...` отдают точную актуальную страницу.
Логи: `target/photoframe-stack80*.log`, `target/photo-*.log`.
