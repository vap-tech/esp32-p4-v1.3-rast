# Журнал ошибок на SD

Первый источник — ошибки чтения/декодирования кадров фоторамки. Модуль
`src/error_journal.rs` принимает произвольный готовый отчёт, остальные источники
подключаются отдельно. Обычный HTTP409 не является аппаратной ошибкой журнала.

## Архив и непросмотренное

- `/SYSTEM/ERRORS/E00000001.JSON` — неизменяемый отчёт.
- `/SYSTEM/ERRORS/UNREAD/E00000001.SEEN` — запись ещё НЕ просмотрена.
- Крестик удаляет маркер через DELETE. JSON остаётся в архиве.

Это исправленная семантика: первоначальный вариант создавал SEEN после
просмотра и заставлял фильтровать всю историю. На плате до перехода были только два уже просмотренных тестовых отчёта: их
JSON сохранены, прежние отметки SEEN из корня ERRORS удалены. В UNREAD для них
маркеры не создавались; просмотренные отчёты остаются просмотренными.

`GET /api/errors?cursor=0` читает только каталог UNREAD, возвращает не более5
имён JSON и `next_cursor` (null при конце). Одна страница ограничена64записями
каталога; архивные JSON не перечисляются. Веб получает только соответствующие
отчёты, показывает5 и кнопку «Следующие5»/«Сначала». Остальные тела не загружаются.
Обновление текущей страницы раз в10с пропускается во время upload/мутаций/cleanup.
Ошибка запроса сохраняет последний подтверждённый список.

Первый publish после запуска один раз сканирует архив+UNREAD для следующего ID.
Это не часть веб-выборки и не выполняется на каждом опросе. Политики удаления
старых отчётов по таймеру/лимиту нет; история удаляется явно.

## Публикация и отказы

Сначала пишется и закрывается `.TMP`, затем создаётся UNREAD-маркер и отчёт
публикуется rename в `.JSON`. API не показывает частичное тело TMP. Если питание
пропало между маркером и rename, веб показывает ожидающий/недоступный отчёт и
повторяет чтение при опросе; TMP остаётся для диагностики. При первом publish
ID резервируются с учётом JSON/TMP и UNREAD-маркеров, чтобы не переиспользовать
номер незавершённой записи. FAT32 не становится журналируемой ФС: восстановление
тома после аварийного питания остаётся отдельной задачей.

Отказ SD/ФС/дескрипторов оставляет исходную ошибку в RAM (`error_saved=false`) и
в USB-логе. Ошибка журнала рекурсивно в него же не пишется; очереди повторной
записи при недоступной SD пока нет.

## Диагностика

Источник, заголовок, uptime события (не календарное время), код, путь,
входной/выходной размер и геометрия JPEG, shown/skipped, тип отказа и все13полей
JPEG/DMA/AXI snapshot. Runtime: кеши, watermark/guard стека,12регистров LCD,
дескрипторы, recovery/poison ФС, TCP counters и Ethernet status. Это доступные
снимки подсистем, не дамп всей RAM. Workspace4096байт, переполнение возвращает
ошибку. SD I/O выполняется кооперативно после закрытия исходного JPEG.
Ссылка «Полная диагностика» открывает JSON, не подтверждая просмотр.

## Проверки

1000архивных JSON и7непросмотренных → страницы5+2, архив в ответы не попадает.
Frontend: ошибка DELETE не скрывает запись, успешный DELETE скрывает, новые
состояния браузера используют только список pending-маркеров.

На плате предыдущий прогон уже сохранил timeout повреждённого JPEG и последующий
Hardware AXI=4 на исправном JPEG. Оба JSON оставлены в истории, stack guard=true.
Восстановление JPEG после ошибочного потока — отдельная незавершённая задача.
Артефакты текущих проверок: `target/error-inbox-*`.

Проверка на плате новой схемы:7pending-маркеров → API/Chromium5+2; DELETE
крестиком убрал только один marker; reset сохранил5+1, исходный JSON доступен.
Отдельно повреждённый JPEG автоматически опубликовал новый JSON и pending-marker,
его подтверждение удалило marker без изменения тела. Тестовые JPEG и fixture
каталоги удалены, тестовый отчёт оставлен в архиве как просмотренный.
134host tests +frontend/photo-tools и браузерные проверки прошли.
