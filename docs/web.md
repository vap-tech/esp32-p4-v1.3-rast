# Flashbox: HTTP-файлы на SD

Собственный HTTP, embedded-fatfs и smoltcp 0.14.0. Файловые GET/PUT теперь
чередуются; [контракт handles и ограничения](file-handles.md).
Без heap и RTOS.
Обычный stage-2 image. Одна задача владеет SD и выбранным сетевым транспортом (EMAC или C6 SDIO).

## Wi-Fi

```sh
python3 scripts/display-control.py --wifi-web 3600
```

Используется встроенный профиль; открыть адрес из `WEB READY`.
SD и C6 работают через разные слоты общего контроллера с сериализацией I/O.
Подробности и ограничения: [wifi.md](wifi.md#веб-файлы-через-wi-fi).

## Запуск Ethernet

```sh
./scripts/flash.sh
python3 scripts/display-control.py --icache on --dcache off --web-run 3600
# Открыть адрес из WEB READY в браузере, например http://192.168.1.167/
```

PHY должен согласовать 100/full, карта — иметь FAT32 в первой MBR partition.
Автоформатирования нет. D-cache OFF / L2=0 проверяются до запуска; запрет
cached EMAC не снимался. Проводной web-run включает I-cache. ESC или Ctrl-C завершает сервер,
останавливает DMA и возвращает USB-консоль; после этого можно запускать снова.
Срок ограничен указанным временем и DHCP lease; renewal/mDNS пока нет.
Остальные USB-команды, touch и media loop во время web-run не обслуживаются.
HTTP-пульт поддерживает состояние, яркость и текстовый буфер; RTC/media через
HTTP пока не запускаются.
LCD scanout продолжает работать аппаратно; совместное WAV+HTTP не заявляется.

## API

| Метод | Путь | Результат |
|---|---|---|
| GET / HEAD | `/`, `/index.html` | HTML из `/www/index.html` на SD, без встроенного fallback |
| GET / HEAD | `/api/list?path=%2F` | chunked JSON `entries` с name/dir/size |
| GET / HEAD | `/fs/DIR/NAME.BIN` | файл, Content-Length, inline и MIME по расширению |
| GET / HEAD | `/fs/DIR/NAME.BIN?download=1` | принудительное скачивание, attachment |
| MKCOL | `/fs/DIR` | новый каталог, 201 |
| DELETE | `/fs/DIR/NAME.BIN` | файл или пустой каталог, 204 |
| POST | `/api/rename?path=%2FDIR%2FOLD.TXT&name=NEW.TXT` | новое имя в том же каталоге, 204 |
| GET / HEAD | `/api/state` | brightness, uptime_us, capacity_bytes, clipboard_limit |
| POST | `/api/brightness?value=25` | яркость 0..100, 204 |
| GET / HEAD | `/api/clipboard` | текст UTF-8 |
| POST | `/api/clipboard` | заменить текст, Content-Length <=1024, 204 |
| PUT | `/fs/DIR/NAME.BIN` | потоковое create-new, 201 после finish |

Пути percent-decoded UTF-8, максимум 768 B включая начальный `/`. Имена FAT LFN
до 255 UTF-16 units на компонент, без `.`/`..` компонентов. Имена не обрезаются. Существующий файл — 409,
отсутствующий — 404, неверное имя — 400, полный том — 507, dirty volume — 503.
Создание каталогов поддерживает `.`/`..` и расширение цепочки каталога при
заполнении. Удаление на backend ограничено файлами и пустыми каталогами:
непустая папка —409. Браузер после подтверждения обходит дерево и последовательно
удаляет детей, затем родителя; операция не атомарна, прерванное удаление может
оставить часть дерева. Rename не перемещает между папками и не перезаписывает
существующие имена. Read-only entries и импортированные LFN aliases пока нельзя
удалять/переименовывать: не оставляем привязанные long-name slots повреждёнными.
Overwrite/append и создание LFN пока не реализованы. Modified не
выдаётся: календарь платы пока невалиден, UI показывает прочерк.

PUT требует Content-Length <= u32::MAX, включая нулевую длину. Отсутствующая
длина — 411; Transfer-Encoding (включая chunked upload) — 501; сжатое тело —
415. Дубли Content-Length/Host и недопустимые заголовки отвергаются. Поддержан
Expect: 100-continue; файл открывается до interim response, поэтому конфликт
не требует загрузки тела. Один запрос на TCP connection, Connection: close. Для HTTP/1.0 listing
использует завершение по закрытию соединения вместо chunked.
Потоковый writer держит 512-B edge buffer, файл не буферизуется целиком.
При EOF/reset/таймауте/ESC до полного тела вызывается abort; при SD I/O error
отката нет, том остаётся dirty. Отключение питания всё ещё требует внешнего fsck.
Потерянный ответ после успешного finish не откатывает уже опубликованный файл.

## Память и Flash-assets (исторически, до2026-11-17)

Встроенный веб удалён; актуальные команды восстановления, ограничения перезаписи
и замеры находятся в [web-sd-page.md](web-sd-page.md). Описание ниже — история.

`pack-image.py INPUT OUTPUT frontend/index.html` детерминированно gzip-сжимает
актуальную страницу и добавляет отдельный Flash slot по **0x100000**:
16-B header `<8sII>` = `P4WEB001`, длина, CRC32, далее gzip, padding до 4 B.
Максимум asset 64 KiB; перекрытие runtime с asset slot — ошибка сборки.
Старый вызов packer без HTML остаётся доступен для loader tests, но такой образ
не содержит страницы. `image.sh` всегда упаковывает HTML.

Asset не входит в `.upper` и не занимает постоянную SRAM-копию. До запуска
сервера header/CRC проверяются ROM Flash read; отдача идёт кусками по 1024 B
через SRAM workspace. Не используется XIP или параллельная запись Flash.
Большой FF gap увеличивает firmware.bin примерно до 1 MiB; это не размер runtime.
Старые stage-2 измерения 420656 B относятся к образу без HTTP/assets.

TCP/IP: smoltcp0.14.0, четыре фиксированных sockets. На каждое6КиБ RX и16КиБ
TX, всего88КиБ SRAM для очередей; HTTP header отдельно ограничен2048B (431).
Очереди не размещены в PSRAM и не отдаются напрямую DMA: драйвер синхронно
копирует кадр через свой workspace. Единственный владелец сервера заимствует
статические очереди до завершения; новый запуск возможен после drop предыдущего.
Socket metadata и frame buffers также статические/фиксированные, heap нет.

Включены Ethernet, IPv4, TCP, ICMP echo и целочисленный Reno. Отключены
std/alloc, async, IPv6, IP fragmentation, UDP-сокеты и Cubic с f64.
DHCP пока остаётся собственным ограниченным клиентом; после lease smoltcp
получает IP/mask/default route и сам обслуживает ARP/ICMP/TCP. Для EMAC и C6
используется общий Device adapter, MTU1514 включая Ethernet header.

Скользящее окно, ACK/RTO/повторы, сборка out-of-order потока, congestion control
и FIN/TIME_WAIT принадлежат smoltcp. RX backpressure ограничен очередью, время
сетевой операции без завершения ограничено30с. Nagle и delayed ACK на борде
отключены. Живые соединения и незавершённый FIN сохраняют свой socket. Повторный
listen следует публичному контракту smoltcp: !is_open() (Closed/TimeWait).
Пул имеет4 места; отдельного долгоживущего TIME_WAIT cache нет. Файловый обработчик обслуживает запросы по очереди.
Неполный header одного соединения не блокирует готовый header другого.

HTTP flush теперь публикует данные в TCP-очередь, не ждёт ACK каждого MSS.
Перед штатным close отдельный finish дожидается подтверждения всей очереди;
при ошибке socket abort. Network.tick ограничен16 RX/16 TX за вызов,
периодически проверяет ESC/deadline и последовательно использует общий Timer.
Внутри драйвера DMA остаётся синхронным; Embassy и IRQ-планировщик не добавлены.

## Проверки на плате

- Chromium: реальная страница, listing, выбор двух файлов, последовательные PUT,
  refresh и скачивание с проверкой содержимого. Без mock backend.
- 262148 B и 1048580 B PUT/GET совпали побайтно. Последний 1-MiB run
  с Expect: 100-continue: около 340 KB/s upload и 943 KB/s download,
  параллельные 20 ping без потерь. Wi-Fi/маршрутизатор ноутбука включены в замер;
  это не предел SD/EMAC.
- Повторный PUT — 409; HEAD, 404, invalid name/traversal, пустой файл.
- PUT оборван после 3000 из 9000 B: файл не опубликован, последующий create
  работает. Маленькое RX window клиента и пауза чтения 2 s прошли без порчи.
- Незавершённый header на одном socket не блокирует listing на другом.
- Перепрошивка/повторный mount сохранили записанные файлы. Guards/stack проверяются
  после остановки; измерения и скриншот — ignored `target/web/`.

Host tests проверяют TCP retransmit/partial ACK/duplicate/RST/window/wraparound,
строгий HTTP framing/пути/JSON, HTTP поверх FAT32 с короткими частями тела,
abort/conflict/GET/HEAD/list. Python проверяет упаковку assets/CRC/границы.
Протокольные ориентиры: [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html),
[HTTP/1.1 RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html).

Финальная проверка остановки: RX errors=0, TCP retransmit=1 с успешным
восстановлением, DMA pool used=0 после Drop/reset (peak 19328 B), stack peak
12628/16384 B и guard intact. D-cache ON отвергнут с CacheConfiguration, после
возврата D OFF сервер запускается снова. Default payload около 189 KiB,
BSS 42.25 KiB, work 265 KiB; страница gzip 5730 B отдельно во Flash.


## Панель файлов и управление, 2026-11-12

Имя файла открывает отдельную вкладку для поддерживаемых браузером форматов
(JPEG/PNG/GIF/WebP, WAV/MP3, TXT/LOG/CSV, PDF). Неизвестные форматы — octet-stream.
HTML с карты не запускается как панель: Content-Security-Policy sandbox и nosniff.
В нативном select `⋮`: открыть, скачать, переименовать, удалить. Нативные prompt/
confirm запрашивают имя и подтверждают удаление. Это не требует JS-библиотеки.

Загрузка папки через chooser сохраняет относительные пути. Drag-and-drop
обходит FileSystemEntry и поддерживает также пустые папки. Все операции
создания папок/PUT идут последовательно; назначение фиксируется при добавлении.
Переход по каталогам не перенаправляет очередь. Неверные FAT-компоненты и пути
длиннее 768 UTF-8 байт отвергаются, имена не сокращаются. Созданная часть дерева
остаётся, если другой файл не загрузился. Существующие файлы не заменяются.
Операции rename/delete не стартуют во время очереди, загрузки, добавленные
во время удаления, ждут окончания действия.

Буфер —1024 байта UTF-8, статический в SRAM, без исполнения команд, сохраняется
между web-run в пределах одного запуска прошивки; после reset пуст.
Оборванный POST или неверный UTF-8 не меняет старый текст. Это пока заготовка
для общих потребителей текста, не интеграция с редактором/системным clipboard.
Состояние обновляется кнопкой; яркость меняется через существующий Display API.
Нет новых heap/RTOS/Cargo-зависимостей. Ограничения одного обслуживаемого
файлового запроса и отсутствия HTTP+media кооперации сохраняются.

## Тест сети без SD

В «Управление бордой» кнопка «Тест скорости сети» выполняет последовательно
скачивание из SRAM и загрузку в SRAM. Объём256 КиБ /1 МиБ /4 МиБ на направление.
Браузер показывает КиБ/с, Мбит/с, полное время HTTP и прогресс скачивания;
«Отмена» прерывает fetch. Повторяющийся байтовый шаблон скачивания проверяется.
POST подтверждает число принятых байтов; данные не сохраняются.

`GET /api/net-test?bytes=262144` — octet-stream, Content-Length, no-store.
`POST /api/net-test?bytes=262144` с таким же Content-Length — JSON received.
HEAD тоже поддержан. Допустимо1..4194304B, несовпадение длины400, отсутствие
Content-Length у POST411. Один8-КиБ SRAM scratch, без SD/PSRAM/Flash-asset I/O
в обработчике. Передача и ожидания кооперативно вызывают Network.tick();
обслуживание других HTTP-запросов остаётся последовательным. Тест запускайте
без параллельной загрузки файлов. Он измеряет весь тракт браузер–TCP/HTTP P4–
SDIO–C6–Wi-Fi, включая повторы, а не отдельно скорость PHY или предел радио.
В demo кнопка отключена, чтобы не показывать фиктивные сетевые результаты.

Первый аппаратный RAM-only прогон262144B:4,21КиБ/с download,19,15КиБ/с upload.
Оба направления завершились; download совпал с шаблоном. Это подтверждает,
что низкая end-to-end скорость воспроизводится без обращений к SD.

## Async FAT и длинные имена — 2026-11-13

Веб-файлы теперь обслуживает embedded-fatfs через IRQ-driven SDMMC. Поддержаны
LFN, UTF-8 пути, пробелы и кириллица, до 255 UTF-16 units на имя / 768 UTF-8 байт
на путь. Прежние ограничения 8.3/96 байт выше относятся к старой реализации.
Формат HTTP API сохранён. Файловые операции всё ещё последовательные.
[Контракты, отмена, память и оставшиеся ограничения](async-storage.md).

## Несколько открытых файлов

GET/PUT файлов теперь чередуются на четырёх TCP slots, общий FileTable имеет
настраиваемую ёмкость (сейчас5). Нет отдельного8-KiB буфера на каждый файл.
Остальные endpoints пока синхронные; frontend queue по-прежнему последовательная.
[Контракты, память, отмена, ограничения и проверки](file-handles.md).


## Статические ресурсы `/www`

`GET`/`HEAD /www/...` отдают точный файл с SD; `/assets/app.js` также ищется
как `/www/assets/app.js`. `/www` и путь с завершающим `/` ищут `index.html`.
Query для version/cache-busting не участвует в имени файла. Есть MIME для
HTML, JS/MJS, CSS, JSON/map, WASM, SVG, ICO, WOFF/WOFF2, TTF/OTF и webmanifest;
неизвестное расширение — application/octet-stream. Бинарные данные не преобразуются.
Запись ресурсов — через обычный `/fs/www/...`, static namespace только read-only.
Неизвестные `/api/...` не становятся файлами, `..` и percent-encoded traversal
отвергаются. `/flash` ранее был встроенной аварийной страницей; с2026-11-17 удалён.

`/www` — доверенный код админки, поэтому static-ответ не получает CSP sandbox;
иначе скрипты/модули/worker не заработают. `nosniff` сохранён. Произвольные
пользовательские HTML/JS через `/fs/...` по-прежнему отдаются с CSP sandbox
(или attachment при download=1). Размещать исполняемый код следует осознанно в `/www`.

## Удаление без ожидания всего файла в основном HTTP loop

DELETE теперь отдельная порционная передача: до128кластеров и пакетная запись
FAT за проход. HTTP204 означает завершённое освобождение места и checkpoint.
Имя удаляется при старте; закрытие вкладки не прерывает начатое освобождение.
Другие HTTP-запросы обслуживаются между шагами, повторное удаление во время
активного job получает409. [Порядок записи, ошибки и ограничения питания](fat-writeback.md#порционное-удаление-2026-11-16).

В вебе отдельный статус: «Идёт удаление: /путь · время. Подождите…». Для дерева
показывается текущий дочерний файл, каталог удаляется после детей. Процентов
и оценки времени нет. «Удалено» появляется после подтверждения всех DELETE;
при обрыве связи — «не подтверждено», с пояснением, что плата продолжает работу.
Таймер убирается и при успехе, и при ошибке. Статус не зависит от обновления
списка/перехода в другую папку; новые загрузки в этой вкладке ждут конца действия.

## Отказ загрузки без обрыва тела, 2026-11-17

Для файлового PUT/POST при отказе открытия (включая существующее имя →409)
или нехватке upload staging (503) сохраняются код ответа и остаток Content-Length.
Тело вычитывается кооперативно через smoltcp `recv`: байты удаляются из RX ring
без копирования в SRAM scratch/PSRAM и без создания файлового дескриптора.
За один turn потребляется не более8192байт. Финальный HTTP-ответ отправляется
после полного приёма тела, затем обычный flush/close. Для Expect:100-continue
сначала отправляется100, чтобы клиент начал тело. Нулевое тело отвечает сразу.
Обрыв и30с без прогресса проходят обычный cancel/abort; остальные слоты работают.
Это не предварительный HEAD: на файл остаётся один PUT. Цена конфликта — полная
передача файла по сети без записи на SD.

Проверка на rev1.3: 0/64КиБ/8МиБ →409; 8МиБ за3,177с, параллельный state≈16мс.
Expect +1МиБ, обрыв на64КиБ и6повторных запросов прошли; SHA256 существующего
index не изменился. Настоящий Chromium XHR8МиБ:409 за3,607с, activeUpload=null.
Host:131тест +5packer tests; discard также проверяется в TCP sliding-window тесте.
Артефакты: `target/http-reject-*`, `target/test-http-reject.py`.
