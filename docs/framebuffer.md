# Один framebuffer: камера → ISP → PSRAM → дисплей

На ESP32-P4 rev 1.3 работает **один полный RGB565 framebuffer 1024×600**,
**1 228 800 байт**, в PSRAM. Промежуточного полного RAW/RGB-буфера для камеры
нет, CPU пиксели камеры не копирует. Cargo-зависимости не добавлены.

Актуальная сводка и незавершённое: [status.md](status.md). **Камера пока даёт
очень тёмное изображение; работа над её качеством отложена.** Разделы с
экспериментами ниже сохраняют историю, а не текущие значения по умолчанию.

## Память и питание

BOYA — SPI flash 16 MiB; её режим в этой работе не меняется.
PSRAM отдельно опознана: AP Memory, MR1 vendor `0x0D`, MR2 `0xDF`, **32 MiB**.

- LDO2 1.8 V питает PSRAM/MSPI. DREF/MUL берутся из eFuse, при отсутствии
  калибровки — номинальная пара 8/4. MSPI PHY дополнительно требует
  `PMU_MSPI_PHY_XPD=1`; без него команда чтения зависала в DIN.
- Источник clock SPLL480, без настройки MPLL: mode registers на 40 MHz
  (делитель 12), AXI-доступ на **80 MHz** (делитель 6), HEX DDR x16.
  Сохранена fixed read latency 10 cycles. Настройки 200/250 MHz не проверены.
- Собственный HAL настраивает питание, pads, MSPI2, timing и MMU. Только команды
  mode registers используют **три функции встроенного mask ROM**:
  `esp_rom_spi_set_op_mode`, `esp_rom_spi_cmd_config`, `esp_rom_spi_cmd_start`,
  адреса ROM ABI eco0…4 `0x4FC00110/108/10C`. Это не SDK/runtime в образе.
  У внутреннего ожидания ROM нет нашего timeout; питание PHY включается до вызова.
- Identity mapping первых **4 MiB**, 64 страницы по 64 KiB. Остальные 28 MiB
  пока не отображаются и не используются. L2 cache для PSRAM не включается.
- CPU пишет/читает **uncached alias `0x88000000`**. DMA использует отображённый
  адрес `0x48000000`. Смешивать CPU cached alias с uncached сейчас нельзя.
- Первые 4 MiB проверяются двумя адресными шаблонами с записью и чтением;
  этот тест деструктивный и запрещён, когда память уже принадлежит framebuffer.

Framebuffer DMA address **`0x48000080`**, CPU address **`0x88000080`**.
До и после него — защитные области по 128 B, заполненные `0x5AA55AA5`.
`devices::framebuffer::Framebuffer` забирает `Psram` во владение, heap не нужен.
Старый маленький RAW-буфер 64×32 в SRAM сохранён только для команд `A/o`.

## Вывод дисплея

DW-GDMA **channel 1 / аппаратный CH2** читает полный framebuffer и пишет
в DSI FIFO **`0x50105000`**. Source и destination настроены на автоматическую
перезагрузку после блока: развёртка продолжается аппаратно без ISR и CPU rearm.
Главный цикл и блокирующая USB-консоль больше не обслуживают каждый LCD-кадр.

DSI bridge: RGB565, 1024×600; HS/HBP/HFP=20/136/160,
VS/VBP/VFP=2/12/20. DPI clock фактически **48 MHz**, host HLINE=1919.
Расчётная развёртка около **56.5 Hz**, не инструментальное измерение.
DSI остаётся 2×550 Mbps; 153 600 элементов по 64 бита на кадр.
`transferred=153599` — аппаратный счётчик minus 1. У LCD приоритет DMA выше.
Ранее DPI снижался до 30 MHz из-за underrun при совместной нагрузке, но
пользователь обнаружил искажение цветов на физическом LCD. Возвращены 48 MHz:
RGB-таблица отображается правильно. Долговременная стабильность camera+LCD
ещё не подтверждена; детали экспериментов ниже.

## Прямая запись камеры

```text
OV02C10: RAW10, 1024×600 crop, 2 CSI lanes
    → CSI host → ISP RAW10 / GBRG → RGB565
    → CSI bridge → DMA channel 0 / CH1
    → тот же framebuffer в PSRAM
    → DMA channel 1 / CH2 → DSI → JD9165
```

Это crop исходных 1920×1080, а не уменьшенная картинка со всего поля зрения.
Сенсор выдаёт RAW10; ISP выполняет demosaic и RGB/YUV-преобразование для RGB565,
BT601 full range, clock PLL240 / 2 = **120 MHz**. AE/AWB/gamma и отдельная
цветовая калибровка ещё не подняты. Экспозиция preview фиксированная: 1120 строк
при сохранённом VTS=1164; маленькая RAW-проба сохраняет прежние 256 строк.

Оба DMA работают с аппаратным reload, ISR/RTOS не используются.
CSI больше не сбрасывает весь DMA при старте/остановке: abort касается только
channel 0; DSI аналогично останавливает только channel 1.
`O` останавливает камеру, оставляя последний framebuffer на дисплее.

Один буфер означает одновременные запись камеры и чтение LCD. Возможны tearing
и смесь частей соседних кадров. Это ожидаемое ограничение выбранной схемы;
защиты памяти и отсутствие underrun не означают отсутствие tearing.

## Команды

После reset по умолчанию включены обычные вертикальные полосы; framebuffer и preview включаются
явно. В текущей сессии после итоговой проверки оставлен live preview.

```bash
python scripts/display-control.py F       # PSRAM test, один framebuffer, RGB565 bars
python scripts/display-control.py G       # тестовый генератор сенсора → framebuffer
python scripts/display-control.py V       # матрица камеры → framebuffer
python scripts/display-control.py S q e   # DMA/ISP/guards, панель, DSI RX error counter
python scripts/display-control.py O       # камера off, последний кадр остаётся
python scripts/display-control.py U       # камера off, scanout off, обратно обычные полосы
```

Повторный `F` выключает камеру и снова рисует полосы в том же буфере.
`P` не делает деструктивный memory test после создания framebuffer.
Прежние команды изменения video/BIST/reset панели при scanout требуют сначала
`U`; `?`, `q`, `e`, `i/I` доступны. Старая RAW-проба `A/o` при live требует сначала `O`.

`S` читает/очищает накопленные ошибки bridge/ISP, host errors — read-to-clear.
`FRAMEBUFFER DMA` содержит `[CHEN, CH2 events, count-1, source, DSI raw errors,
FIFO depth, DPI config, DMA flow config, bridge pixel type, host colour code,
bridge YUV config, DPI update pending]`. `CHEN=3` означает оба активных канала;
после `O` остаётся `2`. Поле DMA events может содержать обычные transaction-complete
события. Ненулевой DSI raw bit 0 — underrun, CSI bridge bits 0…4 — ошибки.

`H` выдаёт thumbnail 128×75: `FB_THUMB`, 75 строк `FBROW` с RGB565 hex и
`CMD H`. Для цельного снимка сначала `O`; при live возможна смесь кадров.
`python scripts/framebuffer-snapshot.py target/camera.png` по умолчанию использует
команду W для полного снимка 1024×600 из отдельной копии PSRAM; `--live`
выбирает старую миниатюру H. PNG сохраняется стандартной библиотекой Python. Во время использования не запускать
параллельно monitor/display-control.

## Проверки и границы результата

Тестовые полосы, считанные из framebuffer после ISP, визуально проверены:
ровные вертикальные белая/жёлтая/голубая/зелёная и начало пурпурной полосы,
как и ожидается от crop шириной 1024 из исходных 1920. Полосы из CPU framebuffer
тоже имеют ожидаемые RGB565-значения. Позднее пользователь подтвердил по фото
правильные цвета физического LCD на 48 MHz (см. историю ниже).

Первый снимок матрицы был почти чёрным из-за некорректного analogue gain в
заимствованной таблице: 0x4000 в 0x3508/09 за допустимым диапазоном. После явной
установки корректного gain появились свет и контуры объектов. В первоначальной
пробе analogue был 8x; сейчас analogue/digital 1x/1x. AE/AWB ещё нет.
Пользователь подтвердил изображение люстры на физическом LCD; картинка пока
тёмная. Доступны ручные настройки ниже, AE/AWB и gamma ещё не реализованы.
Логи и снимки: `target/framebuffer-*.log`, `target/camera-framebuffer-*.log`,
`target/camera-0.png` (генератор), `target/camera-1.png` (матрица).

Итоговые логи: `target/framebuffer-30mhz.log`, `target/framebuffer-check.json`.
Проверены F/G/V/O/U и повторный запуск: оба DMA активны при preview, после O
остаётся только LCD; guards целы, CSI CRC/ECC/PHY errors = 0, LCD RX errors = 0.
Cargo fmt, clippy с `-D warnings` и 8 host-тестов проходят. После добавления ручных настроек текущий образ 46 560 B.

В SRAM добавлен минимальный trap handler: печатает mcause/mepc/mtval и останавливает
CPU. Это помогает отличать access fault от зависания периферийной транзакции;
обработки IRQ и восстановления после исключений он не добавляет.


## Исправление чёрного изображения OV02C10

Рабочий формат управления сверён с
[Linux OV02C10](https://github.com/torvalds/linux/blob/master/drivers/media/i2c/ov02c10.c):
analog control 0x10…0xF8 (Q4) записывается в 16-bit register 0x3508 со сдвигом
на 4; итоговый диапазон 0x0100…0x0F80. Digital control 0x0400 для 1x
записывается в 24-bit register 0x350A со сдвигом на 6, то есть 01 00 00.
В таблице PR было 0x3508=40, 0x3509=00 — недопустимый analogue 0x4000.
Инициализация теперь явно переопределяет gain после таблицы; Snapshot показывает
все пять gain-байтов, включая 0x350C. При 1x свет появился, но изображение было
тёмным; для начального indoor preview выбрано 8x. Это не автоэкспозиция.
Аппаратные логи: `target/camera-gain-fixed.log`, `target/camera-gain8-live.log`;
снимки: `target/camera-gain-fixed.png` (1x), `target/camera-gain8.png` (8x).


## Ручная яркость камеры и подсветка

Команды меняют параметры без остановки preview. Например:

```sh
python scripts/display-control.py ']'  # цифровое усиление вдвое больше
python scripts/display-control.py '['  # цифровое усиление вдвое меньше
python scripts/display-control.py '+'  # подсветка LCD +5 процентных пунктов
python scripts/display-control.py '='  # прочитать реальные настройки
```

| Команды | Параметр | Шаг и пределы консоли |
| --- | --- | --- |
| `]` / `[` | Digital gain камеры | ×2 / ÷2, 1…8x |
| `}` / `{` | Analogue gain камеры | ×2 / ÷2, 1…15.5x, насыщение на границах |
| `>` / `<` | Экспозиция | ±128 строк, 4…1156 |
| `+` / `-` | Подсветка LCD | ±5 процентных пунктов, 0…100% |
| `=` | Чтение gain, exposure и подсветки | Q4 / 16 = analogue; Q10 / 1024 = digital |

Начальные значения: exposure 1120 строк, analogue 1x, digital 1x, LCD 25%.
Экспозиция ограничена VTS−8 и проверяется перед записью; изменение FPS здесь
не поддерживается. Настройки камеры сохраняются при повторном V/G в рамках
одного запуска, сброс возвращает начальные значения. Перед настройкой камеры
нужен live preview (`F V`). Подсветка доступна и без него.

Публичный API драйвера: `Controls`, `read_controls`, `set_controls`.
Диапазон API digital шире консоли: Q10 1024…16383. Все значения проверяются
перед записью, но несколько SCCB-записей не атомарны: ошибка шины может оставить
частично обновлённые настройки, поэтому консоль всегда читает их обратно.
Усиление повышает шум и может обрезать светлые участки; подсветка меняет только
светимость LCD, а не данные изображения.

На плате проверены обе стороны каждой регулировки с чтением регистров,
затем поток и guards: CSI/DSI errors = 0, guards=true.
Лог: `target/camera-controls.log`. Для просмотра оставлено digital 2x, LCD 5%.


## Полный screenshot

`python scripts/framebuffer-snapshot.py target/camera-full.png` теперь сохраняет
все 1024×600 RGB565-пикселей без прореживания и увеличения. Команда прошивки `W`
останавливает только CSI DMA, копирует 1 228 800 байт в отдельную область PSRAM
на смещении 2 MiB и возобновляет CSI, затем передаёт копию строками hex по USB.
LCD продолжает работать. Передача занимает несколько секунд, буфер копии в это
время камера не меняет. Зарезервированы, отображены и проверяются 4 MiB PSRAM;
постоянный framebuffer остаётся один, копия используется только для screenshot.

Остановка DMA пока не синхронизирована с концом кадра: возможно смешение двух
соседних кадров на одной горизонтальной границе. Копия стабильна во всё время
USB-передачи; строгий захват одного sensor frame потребует остановки по EOF.
`--live` оставлен для старой миниатюры H 128×75; `--scale` по умолчанию 1.
После прошивки поднят F/V и digital 2x, захвачен `target/camera-full.png`.

Контрольный screenshot CPU-полос: все 614 400 пикселей PNG побайтно совпали
с ожидаемыми восемью цветами RGB. После screenshot камеры проверены live=true,
guards=true, CSI/DSI errors=0. После теста полос камера возобновлена через V.


## Проверка цвета LCD отдельно от камеры

`F E` останавливает камеру и выводит из того же RGB565 framebuffer:
верхние 300 строк — 32 ступени серого от чёрного слева до белого справа;
строки 300…449 — чистые красный, зелёный, синий слева направо;
строки 450…599 — соответствующие градиенты от чёрного сверху до полного цвета снизу.
RGB565-серый использует расширение зелёного 5→6 бит с повтором старшего бита.
Подсветка остаётся 5%. `V` возвращает камеру (после сброса настройки начальные).
Полный эталонный screenshot: `target/color-check.png`, лог: `target/color-check.log`.
Внешний вид на LCD оценивает пользователь; данные PNG сами по себе его не подтверждают.


### Диагностика порядка байтов по фото LCD

Фото пользователя: вместо R/G/B получились голубой/розовый/болотный. Это
соответствует интерпретации byte-swapped RGB565: F800→00F8, 07E0→E007,
001F→1F00. Для проверки **только E** теперь пишет `color.swap_bytes()`.
Выведено F/E, лог `target/color-check-swapped.log`; визуальное подтверждение
новой таблицы ещё ожидается. F, камера и PNG-декодер пока используют прежний
порядок, глобальное исправление до подтверждения не сделано. Старый
`target/color-check.png` — эталон до экспериментального swap.


### Byte swap не подтвердился; чтение панели

Второе фото пользователя после swap: серая шкала распалась на повторяющиеся
цветные группы; swap **убран** из E. Ранее заявленная причина не подтверждена.
Команда Q временно заливает весь framebuffer чёрным/R/G/B/белым и читает
JD9165 DCS 06/07/08, затем возвращает таблицу E. Проверены отдельно записи u32
и u16: в обоих случаях панель возвращает [0,0,0], [62,0,0], [0,63,0],
[0,0,62], [62,63,62]. Логи `target/color-probe.log`, `target/color-probe-width.log`.
Это подтверждает RGB на точке чтения контроллера, но не оптический цвет LCD.
S теперь дополнительно показывает bridge pixel_type, host color coding,
bridge YUV config и pending DPI update: 2/0/0/0, как у SDK RGB565 config0.

Для проверки отображения после приёма данных разрешены i/I при framebuffer
scanout: DCS INVON/INVOFF. Сейчас оставлена E с INVON (image status=0x20),
подсветкой 5%, камера остановлена. Лог `target/color-inversion.log`.
Результат на физическом LCD ожидает подтверждения; причина пока не установлена.
На запуске F наблюдается единичный флаг underrun; это не CRC-ошибка и само по
себе не объясняет стабильное изменение цветов во всём изображении.


### Старт без BER

По просьбе пользователя стартовый шаблон Display изменён с BER на обычные
вертикальные цветные полосы (Pattern::Vertical), инверсия по умолчанию выключена.
Проверен цикл boot → F/E → U; после U остаются обычные полосы, image status=0.
Лог `target/display-vertical-start.log`. При framebuffer scanout регистр
HOST_VID_MODE_CFG явно записывается как 0xBF02: VPG_EN и BER_MODE выключены.
Сам факт старта с BER пока не подтверждён как причина искажения цвета.
Сейчас на плате оставлены обычные аппаратные вертикальные полосы.


### История проверки частоты при неправильных цветах

После старта без BER пользователь снова сфотографировал неверные цвета E.
Это исключает устранение проблемы одной сменой стартового шаблона. Старый
IDF-код запрашивает DPI 50 MHz (реальный делитель PLL240/5 даёт 48 MHz),
а наш scanout был снижен до 30 MHz. Для изолированной проверки **временно**
выставлены 48 MHz в start_framebuffer, host HSA/HBP/HLINE пересчитаны от
реальной частоты (делитель формулы 384 вместо 240). Таблица E остаётся RGB565
без swap, INVON выключен. Камера **не включена**: совместный поток при 48 MHz
ранее давал underrun; это диагностический режим, не подтверждённая новая
рабочая частота preview. Лог `target/color-check-48mhz.log`, guards=true,
ошибки пакетов панели=0; при запуске был единичный флаг underrun.
Визуальный результат на LCD пока ожидается. Ранее описанные 30 MHz относятся
к предыдущему проверенному совместному режиму камера+LCD.


### Текущие значения по умолчанию после сравнения камеры

Пользователь подтвердил по фото правильные RGB-цвета E при DPI 48 MHz;
при 30 MHz они были искажены. Причина зависимости оптического результата
от частоты пока не выяснена. Preview оставлен на 48 MHz без дополнительных
компенсаций, один буфер. Для снижения усиления пользователь запросил analogue 1x.
Перед изменением считаны его текущие настройки: digital 8x, подсветка 25%.
Они сохранены как defaults; exposure остаётся 1120 строк. Controls::preview:
analogue_q4=16, digital_q10=8192; Display::new brightness=25.
Инициализация сенсора также исправлена на analogue 1x до применения controls.
После перепрошивки F/V и чтение регистров подтвердили именно эти значения,
guards=true, CSI errors=0, DSI underrun flag=0 в проверенном окне.
Лог `target/camera-unity-defaults.log`. Камера оставлена включённой.
Исторические 5%, gain 8x/1x и 30 MHz выше описывают предыдущие эксперименты.

Следующее изменение по запросу пользователя: digital также снижен до 1x
(Q10=1024) в Controls::preview. Оба gain теперь 1x, подсветка по умолчанию
25%. После перепрошивки камера включена F/V, регистры прочитаны обратно;
лог `target/camera-unity-both.log`.

Эксперимент с BF, CCM white balance и gamma отменён по результату на LCD
и просьбе пользователя. Код обработки удалён, прежний preview восстановлен:
оба gain 1x, подсветка 25%, DPI 48 MHz.
