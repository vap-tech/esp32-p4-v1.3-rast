# Кольцевой приём HTTP в PSRAM — 2026-11-14

Вместо одного буфера на upload теперь используется кольцо. Штатный размер
задаётся константами `web::upload::{BLOCKS,BLOCK}`, варианты для измерения:

```sh
P4_UPLOAD_BLOCKS=2 P4_UPLOAD_BLOCK_KIB=32 ./scripts/image.sh
P4_UPLOAD_BLOCKS=2 P4_UPLOAD_BLOCK_KIB=64 ./scripts/image.sh
P4_UPLOAD_BLOCKS=3 P4_UPLOAD_BLOCK_KIB=32 ./scripts/image.sh
P4_UPLOAD_BLOCKS=3 P4_UPLOAD_BLOCK_KIB=64 ./scripts/image.sh
```

Без переменных выбран 2×32 КиБ. build.rs проверяет значения и отслеживает
изменения окружения; это параметры сборки, не переключение живого DMA.

Это приёмный кеш данных файла, не увеличение четырёхсекторного кеша FAT.
На каждый непустой активный PUT выделяется одно непрерывное кольцо в PSRAM,
плюс 128 байт guards. Аллокации ленивые, переиспользуются между TCP-слотами
до конца web-run. Максимум 4 параллельных загрузки, отдельное кольцо каждой;
размеры 64/128/96/192 КиБ на загрузку соответственно. SRAM scratch 8 КиБ,
SD bounce 8 КиБ и лимит FileTable/прямого SD-запроса 32 КиБ сохраняются.
64-КиБ блок кольца не означает 64-КиБ DMA-транзакцию.

Курсор head и счётчик queued описывают непрерывную логическую очередь с wrap.
При ожидании `FileTable::write` future опрашивается вместе с приёмом TCP:
уже полученные байты забираются из TCP RX и копируются в свободную часть кольца.
Фоновая часть не вызывает ФС и не запускает второй запрос SD. Один CPU,
один текущий запрос ФС; ни потоков, ни ISR-копирования, ни heap на пакет.

`UploadPool::parts` безопасно разделяет кольцо на неизменяемый источник SD и
два непересекающихся изменяемых диапазона. Производитель пишет только свободные
байты, сохраняя источник неизменным до завершения await. Затем head сдвигается
на фактически записанное количество. При полном кольце TCP создаёт backpressure.
Отправка начинается после накопления BLOCK либо получения всего короткого тела.
Последний хвост точной длины; ответ 201 только после опустошения кольца и close.
Обрыв abort-ит CreateNew, освобождает очередь; незаписанные байты не публикуются.

Условия DMA прежние: D-cache OFF, L2=0, uncached PSRAM; CPU-копирование сохраняет
fence/паузу 320 тактов на 64 байта ради LCD. Кольцо позволяет перекрыть ожидание SD
приёмом сети, но не устраняет стоимость копирования и ограничения карты.
Пока обслуживается ФС одного клиента, дополнительный приём работает для его
кольца; остальные transfer-состояния обслуживаются внешним round-robin циклом.

Телеметрия: WEB RING задаёт конфигурацию; WEB RING USE показывает байты, принятые
во время ожидания SD, и пик queued (включает текущий DMA-источник).
`fs_write_us` диагностического профиля теперь включает перекрывающееся
CPU-копирование; складывать его с copy_us как независимые затраты нельзя.

Повторяемый тест создаёт уникальный файл, сравнивает весь результат и удаляет
его, проверяя неизменность каталога:

```sh
python3 scripts/benchmark-upload.py --size-mib 64 --output /tmp/ring.json
```

Результаты аппаратных проверок приведены ниже. Это отдельные прогоны на одной
карте/проводном соединении, не статистически достоверная разница долей процента.

| Кольцо | PUT 64 МиБ, с | PUT, МиБ/с | GET, МиБ/с |
| --- | ---: | ---: | ---: |
| Один 32-КиБ буфер + FAT cache (предыдущий этап) | 29,883 | 2,142 | 3,691 |
| 2×32 КиБ | 23,808 | 2,688 | 3,710 |
| 2×64 КиБ | 23,781 | 2,691 | 3,677 |
| 3×32 КиБ | 23,313 | 2,745 | 3,721 |
| 3×64 КиБ | 24,278 | 2,636 | 3,719 |
| 2×32 КиБ, повтор итоговой сборки с TCP capture | 24,730 | 2,588 | 3,719 |

Выбран 2×32 КиБ: заметного устойчивого выигрыша от большего кольца пока нет.
Ускорение относительно одиночного буфера около 21–26%; результаты разных карт
и больших пользовательских загрузок могут отличаться.

В 3×32 при ожидании SD принято 18088184 байта, peak queued 98304/98304.
В итоговом 2×32: 15553024 байта, peak 65536/65536. За каждый 64-МиБ PUT —
2048 прямых запросов по 32 КиБ; это фактическая работа PSRAM → SD DMA.

TCP capture итогового PUT: 24,730 с, 10750 интервалов объявленного бордой
нулевого окна, суммарно 12,370 с. Повторных/перекрывающихся payload-диапазонов
в захвате не найдено, tcpdump kernel drops=0. Объявленное окно — поле пакетов
борда → ноут, даже когда полезные данные идут в обратную сторону. Linux GSO/GRO
означает, что число пакетов захвата не равно числу физических Ethernet-кадров.
Сравнения zero-window с одиночным буфером **при том же FAT cache** пока нет;
старые 37,61 с относились к этапу до write-back FAT, это другой эксперимент.

Во всех четырёх конфигурациях 64-МиБ содержимое сравнилось целиком, тестовые файлы
удалены, исходный root сохранён. Хостовые тесты для каждого размера включают wrap,
полное заполнение свободных диапазонов при удержании DMA-источника, точный порядок
байтов и guards. Короткие файлы 0/1/511/512/513/32767/32768/32769/65539 байт,
два параллельных файла с хвостами и оборванное тело прошли на плате.

Ограничение TCP прежнее — всего 4 соединения. Пятый connect может получить RST,
в том числе сразу после HTTP-ответа, пока предыдущий TCP-слот ещё закрывается.
Это не ошибка кольца/данных. Для проверки четырёх загрузок последующие GET
выполняются отдельной фазой после освобождения соединений.

Итоговая сессия: четыре одновременных PUT по 2 МиБ + разный хвост, затем чтение
всех четырёх и удаление — содержимое точное, root неизменён. Пул достиг ровно
4 колец: external high_water 262656 байт (4×(65536+128)). После остановки
external used=0, DMA used=0; DMA high_water 117632 байта, рабочая SRAM 182208 байт.
Стек 55216/65536 байт, guard_ok=true. Предыдущая короткая серия на первой сборке
давала пик 58180/65536, также без нарушения guards. 95 хостовых тестов прошли
для всех четырёх конфигураций, all-features Clippy без предупреждений, 5 packer-тестов.

## Проверка SRAM bounce 8 → 16 → 32 КиБ

Тот же файл 64 МиБ, PSRAM-кольцо 2×32 КиБ, HTTP scratch 8 КиБ, I-cache ON,
D-cache OFF, L2=0. Меняли только ёмкость SD DMA bounce/MAX_TRANSFER.

| SD bounce | PUT, МиБ/с | GET, МиБ/с |
| --- | ---: | ---: |
| 8 КиБ | 2.668 | 3.708 |
| 16 КиБ | 2.648 | 3.725 |
| 32 КиБ | 2.678 | 3.717 |

Заметного эффекта нет. У каждого PUT ровно 2048 прямых запросов по 32 КиБ
из PSRAM: bounce обходится. GET через общий 8-КиБ HTTP scratch не запрашивает
больше 8 КиБ за раз, поэтому дополнительная ёмкость bounce здесь не используется.
Это результат для **увеличения SD bounce**, не тест увеличения HTTP scratch
и не общий вывод о пользе кеширования файловой системы.

Повторение: `P4_SD_BOUNCE_KIB=8|16|32 ./scripts/image.sh` (выбрать одно число),
затем прошивка и `scripts/benchmark-upload.py`. Во всех трёх экспериментальных
сборках bounce находится в верхней SRAM BSS: штатный низкий DMA_FIXED имеет
16 КиБ и разделяется с I2S. Так сравнивались одинаковые пути SRAM; резерв низкого
workspace при этом не переразмечали. Без переменной возвращается штатный
8-КиБ буфер в DMA_FIXED. `sd-wide-bench` имеет собственный фиксированный размер
32 КиБ; этот feature в данном тесте не использовался.

Все три файла побайтово совпали, удалены; каталог не изменён. Guard стека цел.
Хостовые тесты с 16 и 32 КиБ: по 95 passed; all-features Clippy прошёл.
По результату на плату возвращена обычная сборка с bounce 8 КиБ.

## Проверка общего HTTP scratch 8 → 16 → 32 КиБ

SD bounce оставлен 8 КиБ, PSRAM-кольцо 2×32 КиБ, TCP RX 6 КиБ / TX 16 КиБ
на соединение. Во всех трёх сборках scratch выделен из рабочей Internal-арены,
не из DMA-арены: он используется CPU и не требует прямого DMA. Это позволяет
выделить 32 КиБ без вытеснения EMAC/TCP-буферов. Main проверяет свободную рабочую
арену перед web-run и сбрасывает её после выхода, в том числе при ошибке.

Параметр сборки: `P4_HTTP_SCRATCH_KIB=8|16|32 ./scripts/image.sh` (одно число).
По умолчанию остаётся 8 КиБ. Сравнивался PUT/GET 64 МиБ:

| HTTP scratch | PUT, МиБ/с | GET, МиБ/с |
| --- | ---: | ---: |
| 8 КиБ | 2.652 | 3.717 |
| 16 КиБ | 2.689 | 3.500 |
| 32 КиБ | 2.649 | 3.493 |

Увеличение не ускорило запись, чтение стало примерно на 6% медленнее. Оставлены
8 КиБ. Это отдельные прогоны; точную причину ухудшения не профилировали. При
интерпретации важно: upload за один приём ограничен также 6-КиБ TCP RX, download
за шаг ограничен свободным TCP TX (не больше 16 КиБ); чтение SD внутри операции
по-прежнему разбивается на 8-КиБ запросы. Поэтому scratch 32 КиБ не означает
32-КиБ сетевую или SD-транзакцию. Возможное объяснение ухудшения download —
более поздняя передача данных в TCP после завершения крупного чтения ФС,
но это пока гипотеза, не измеренная причина.

Содержимое всех файлов совпало побайтово, временные файлы удалены, корневой
каталог сохранён. Guards стека не нарушены.

Итоговая сборка (scratch 8 КиБ из рабочей SRAM): четыре параллельных PUT с
хвостами, точное чтение и cleanup прошли. После остановки working used=0,
high_water=8192; DMA used=0, high_water=109440 (раньше 117632); external used=0,
high_water=262656. Стек 58352/65536, guard_ok=true. 96 Rust tests и all-features
Clippy прошли. `/flash`, `/flash?path=%2Fwww`, `/?flash=1`, `/index.html?flash=1`
проверены GET/HEAD при временно испорченном SD index, затем исходный файл восстановлен.
Логи и JSON: `target/storage-profile/ring/p4-scratch*`, `p4-flash-page*`.
