# Асинхронное хранилище — 2026-11-13

Веб-файлы переведены на `embedded-fatfs` (Rust, MIT), без std, heap, C или RTOS.
Источник и локальные исправления: [UPSTREAM.md](../vendor/embedded-fatfs/UPSTREAM.md).
Файловый интерфейс отделён от конкретной ФС; exFAT пока не реализована.

> Текущая таблица handles и параллельные файловые HTTP transfers:
> [file-handles.md](file-handles.md). Ниже описание исходного async этапа.

## Слои

- `storage::asynchronous::BlockDevice`: async read/write/sync, LBA и размеры u64.
- `Partition`: проверка границ MBR primary partition; GPT пока нет.
- `Stream`: Read/Write/Seek из embedded-io-async, секторный write-through cache
  на 512 B; выровненные передачи до 8 KiB идут прямо в блочный слой.
- `storage::volume::Volume`: список, открытие/seek/read, create-new/write/finish,
  abort, mkdir, rename, remove, sync. Сейчас один backend FAT, без динамического VFS.
- `web::asyncfs`: HTTP-файлы; обычные запросы обслуживаются последовательно.

На каждой операции тома удерживается исключительное владение; одновременно
несколько изменяемых файлов не открываются. Имена — UTF-8, FAT LFN — UTF-16;
до 255 UTF-16 units на компонент, до 768 UTF-8 байт на путь. Веб поддерживает
кириллицу, пробелы, emoji. Общий HTTP header/request limit остаётся 2048 B;
percent-encoding длинных Unicode-путей может упереться в него раньше лимита пути. Невалидные пути и traversal отклоняются.
Без LFN не-ASCII OEM short names пока не декодируются полностью.
FAT ограничивает размер файла 4 GiB−1; 64-битный интерфейс сам по себе этого не снимает.

## SDMMC и общий контроллер с C6

`hal::sdmmc::Request` — автомат reset → DMA → completion → card-ready.
`poll_request` не ждёт завершения в аппаратном цикле. Core0 CLIC принимает
SDMMC IRQ; отдельный SYSTIMER target0 даёт tick 1 ms для timeout/reset progress.
ISR только сохраняет события и будит future. Инициализация карты/переключение
тактов пока синхронные; это ещё не полный async HAL для всех команд.

DMA видит только постоянные внутренние bounce/descriptors, не пользовательский
slice. Отмена активного Request останавливает/сбрасывает DMA и помещает контроллер
в quarantine до явной повторной инициализации. Если аппаратный reset не завершён,
продолжать небезопасно: panic. Отмена не означает откат файловых метаданных.

Веб использует один foreground future и кооперативный network tick, без Embassy.
Пока SD DMA занят, C6 не получает контроллер. Между транзакциями есть явный yield,
чтобы ФС не захватывала шину повторно раньше обслуживания сети. C6 DAT1 IRQ пока
не подключён: сетевой клиент по-прежнему опрашивается. HTTP socket waits также
остаются кооперативными синхронными; это не многозадачный executor.

## Запись и sync

Mutation guard блокирует дальнейшие операции после drop незаконченного writer,
ошибки либо отмены. `finish` закрывает файл, сохраняет метаданные ФС и вызывает
flush underlying stream; SD write ждёт CMD13 READY/TRANSFER. `abort` удаляет
создаваемый файл и делает checkpoint. Это программный sync, без обещания
устойчивости внутреннего кеша самой карты при внезапном отключении питания.

Том, уже помеченный dirty/io-error при mount, доступен только для чтения.
Автоматического fsck, журнала, восстановления потерянных цепочек и атомарного
rename при потере питания нет. Dirty не очищается автоматически после ошибки.

## Память

Runtime stack увеличен до 64 KiB: аппаратный тест обнаружил переполнение 32 KiB
при файловых мутациях. Нижняя SRAM разделена на scoped DMA arena 116 KiB и fixed
workspaces 36 KiB (SD, Wi-Fi, I2S). TCP queues 88 KiB и HTTP scratch 8 KiB
занимают арену только на время сервера. Для Ethernet добавляются его DMA rings.
Статика DMA обнуляется отдельно при boot; ROM-reserved область сохранена.
Work arena начинается после runtime BSS, linker требует хотя бы 32 KiB.
PSRAM и её uncached политика не менялись. Полный текущий runtime уже не помещается
в исторический экспериментальный layout `l2-128`; рабочая сборка — L2=0. Сервер по-прежнему требует D-cache OFF.

## Совместимость

Прежний `storage::fat32` остаётся для консольных JPEG, WAV, записи звука и
лабораторных команд. Форматирование также прежнее, только по явной команде.
Эти владельцы не работают одновременно с веб-томом. Новый FAT backend не означает,
что все медиа-команды уже понимают длинные пути или получили async I/O.
Следующий этап — перенос потребителей на общий API и отдельный backend exFAT,
если он понадобится; переписывать весь HAL/включать runtime для этого не требуется.

## Проверки

Host: реальные FAT32 sector images, принудительный Pending на I/O, LFN/Unicode,
write/read/seek/rename/abort/remount, poisoned writer, обращения выше 4 GiB.
Экспортированный образ отдельно проверяется `fsck.fat -n`.
На плате: чтение списка с кириллицей, запись/побайтовое чтение 65539 B,
rename внутри Unicode-папки, удаление с сохранением исходного списка файлов;
12 reconnect, 3 HTTP clients, оборванные RAM GET/POST, SD PUT/GET 32772 B и JPEG.
Финальный stack watermark и повторный прогон приведены в status.md.
