# Прямой SDMMC DMA из PSRAM — 2026-11-13

Продолжение [исследования размеров записи](sd-write-batching.md). Все порции
**данных** в этом сравнении — 32 КиБ; служебные секторы FAT по-прежнему 512 Б.
CPU 160 МГц, I-cache ON, D-cache OFF, L2=0, PSRAM uncached. LCD непрерывно
читает framebuffer. Один новый файл 8 МиБ, уже выделенная цепочка кластеров.

## Результаты

Четыре варианта выполнены в прямом и обратном порядке на одной цепочке.
Каждый проход включает sync, затем полное чтение через обычный SRAM RX path.
Шаблон меняется между проходами и содержит номер 32-КиБ блока: оставшиеся
данные от предыдущего прохода не могут пройти проверку. Заполнение входного
буфера и проверка чтением находятся вне измеренного времени записи; обновление
8-байтного маркера каждого блока входит в него.

| Исходный буфер | Путь | МиБ/с, два прохода |
| --- | --- | ---: |
| SRAM | копирование в SRAM bounce → SD | 10,27 / 10,31 |
| SRAM | прямой DMA → SD | 14,72 / 14,83 |
| PSRAM | CPU копирует в SRAM bounce → SD | 3,53 / 3,52 |
| PSRAM | прямой DMA → SD | **14,81 / 14,81** |

Это короткие перезаписи, не создание файла, не sustained-тест карты на гигабайтах
и не скорость HTTP. CPU не наполняет всю очередь из сети в этих интервалах.
При записи из PSRAM напрямую DMA переместил ровно 8388608 Б в каждом проходе;
счётчик DIRECT_BYTES подтверждает отсутствие скрытого fallback для данных.
Код метаданных продолжает пользоваться обычным буфером.

## Найденная настройка burst

Первый прямой PSRAM тест дал всего 4,68–4,70 МиБ/с при 14,38–14,67 МиБ/с
из SRAM. FIFOTH.MSIZE оставался нулевым; старый код пытался установить 2
в BMOD.PBL. Для P4 rev1.x PBL — зеркало MSIZE, менять его нужно через FIFOTH.
Это явно описано в локальном IDF:
`components/soc/esp32p4/register/hw_ver1/soc/sdmmc_struct.h`, поле bmod_pbl.
В soc_caps.h также явно задан SOC_SDMMC_PSRAM_DMA_CAPABLE=1.

Теперь FIFOTH = 0x200f000f: MSIZE=2, прежние TX/RX thresholds=15.
После передачи прочитано BMOD=0x00000200, то есть размер действительно принят.
Бесполезные записи в BMOD[10:8] убраны; enable/fixed-burst сохранены.
С этой настройкой прямой PSRAM сравнялся с SRAM. FIFO-настройка включена и
в default; optional Wi-Fi/C6 на железе в этом эксперименте не проверялся.

Следовательно, старые 11,5 МиБ/с записи и 5,7 МиБ/с чтения CPU через uncached
alias не являются пределом PSRAM для DMA. Вариант с CPU-копированием из PSRAM
действительно ограничивается медленным доступом CPU, а прямой путь его исключает.

## Размещение и владение

- Внешний источник: отдельное выделение 32 КиБ + два 64-Б guard из свободной
  PSRAM-арены, за резервом framebuffer. CPU alias 0x88000000 преобразуется
  в DMA alias 0x48000000. Внутренняя SRAM использует исходный адрес.
- Источник выровнен на 64 Б, длина кратна сектору. Дескрипторы остаются в SRAM.
- Только sd-wide-bench предоставляет unsafe request_write_direct: источник
  должен быть живым, неизменяемым и неподвижным до завершения/остановки DMA;
  D-cache bypassed, L2=0, без параллельного кешируемого alias PSRAM.
- Async Card::write удерживает borrow источника до конца future; Request::Drop
  останавливает/сбрасывает IDMAC и при отмене помещает контроллер в quarantine.
  При невозможности остановить канал память не возвращается обычным путём.
- На direct TX нет очистки/инвалидации данных uncached-источника; синхронизация
  дескрипторов и publication fence сохранены. RX пока остаётся через bounce.
- После завершения освобождается тестовая PSRAM-арена (перед началом требуется
  used=0), флаг direct сбрасывается при любом выходе из сравнения.

Большой SRAM bounce не участвует в direct передаче. В диагностическом образе
он и SRAM scratch всё ещё выделены для сравнения вариантов. Чтобы убрать их
из рабочего 32-КиБ пути, нужно отделить размер прямой транзакции/цепочки
дескрипторов от ёмкости малого bounce для метаданных и невыровненных буферов.

## Проверки и текущая интеграция

Все восемь проходов прочитаны и проверены по полному шаблону. PSRAM source
guards, framebuffer guards и stack guard целы; стек 47444/65536 Б.
LCD status before/after сохранён в логе: scanout оставался включён, последние
два поля состояния равны нулю. Это проверка регистров/памяти, не визуальный
детектор кратковременного мерцания. Временный файл удалён.

Host-тесты проверяют отображение CPU/DMA alias, границы и переполнение адресов,
выравнивание, copy fallback, сохранность секторного кеша при ошибке/отмене.
87 тестов sd-wide-bench и Clippy прошли. Default сохраняет лимит 8 КиБ и bounce;
прямой TX и диагностический readback доступны только в sd-wide-bench.
Обычная работа веба автоматически на прямой PSRAM DMA ещё не переключалась.

Воспроизведение: `./scripts/image.sh --features sd-wide-bench`, прошить
firmware.bin, затем `python3 scripts/display-control.py --sd-files-bench 8`.
Профиль теперь сравнивает только 32-КиБ варианты; прежняя матрица 512 Б/2/8/32 КиБ
остаётся историческим измерением. Нельзя запускать при активном аудио/камере
или занятой внешней арене. Сочетания с другими экспериментальными профилями
не проверялись.

Логи: target/storage-profile/p4-direct-bench.log (до исправления MSIZE),
p4-burst-bench.log (MSIZE=2), p4-psram-direct-results.json.

После возврата default с MSIZE=2 прошли reconnect, три параллельных RAM-клиента,
разрыв TCP, неполное тело запроса, SD PUT/GET и чтение HOME.JPG.
До/после всех опытов root одинаковый (37 записей). Пользовательские файлы
не изменялись; framebuffer оставлен активным, обычный Ethernet-веб запущен.
Release diagnostics+wifi+software-jpeg также собран; радио этим не проверялось.
