# Запуск, сбросы и перепрошивка ESP32-P4 rev 1.3

Проверено на нашей Guition 2026-11-04, через USB Serial/JTAG `/dev/ttyACM0`.

## Как стартует наша прошивка

ROM чипа читает образ с **flash `0x2000`**, проверяет его и загружает все инициализированные сегменты в RAM. Точка входа `_start` — **HP TCM `0x30100000`**. В текущем runtime основной код/константы размещены в SRAM с `0x4FF00000`, data/stack — с `0x4FF20000`, initial SP `0x4FF28000`; карта памяти описана в [gt911.md](gt911.md). `_start` включает SRAM clock, устанавливает стек, обнуляет BSS и передаёт управление Rust, который отключает watchdog.

Второго программного загрузчика, ESP-IDF runtime, таблицы разделов и структуры app descriptor в этом пути нет. `0x2000` — смещение хранения во flash; `0x30100000` — адрес исполнения в RAM. После каждого сброса ROM загружает образ заново.

## Проверенная последовательность

```bash
export PATH="$HOME/.cargo/bin:$PATH"
# Остановить работающий монитор: Ctrl+C.
./scripts/flash.sh /dev/ttyACM0
python scripts/monitor.py /dev/ttyACM0
```

Скрипт прошивки собирает образ и записывает его по `0x2000` через espflash. Запись проверяется флешером. Монитор открывается отдельно; одновременно использовать порт для прошивки и мониторинга нельзя.

Наш монитор на Linux явно снимает **DTR и RTS** через `TIOCMBIC`. В проверенной последовательности после этого наблюдался нормальный SPI-старт. Открытие порта и изменение этих линий могут сами вызвать сброс, поэтому монитор не является полностью пассивным наблюдателем. При исчезновении USB-устройства он ждёт и переподключается.

Для обычного аппаратного старта нажать **RESET без зажатого BOOT**. Чтобы вручную войти в download: удерживать BOOT, нажать/отпустить RESET, затем отпустить BOOT. USB-прошивальщик также умеет переводить чип в download автоматически. Проверенный выше путь — USB-сброс и повторная прошивка; отдельный тест полного отключения/включения питания в журнале этой сессии не зафиксирован.

## Как читать лог ROM

| Сообщение | Значение и действие |
|---|---|
| `boot:0x307 (DOWNLOAD(USB/UART0/SPI))`, `waiting for download` | ROM ждёт флешер; наш образ ещё не исполняется. Проверить BOOT и DTR/RTS, использовать наш монитор или RESET без BOOT. Это само по себе не доказывает повреждение образа. |
| `boot:0x30f (SPI_FAST_FLASH_BOOT)` или `boot:0x30c (SPI_FAST_FLASH_BOOT)` | В этой сессии оба значения наблюдались при старте из flash. Ориентироваться на расшифровку режима; не требовать одного фиксированного числового значения. |
| `load:0x30100000,len:...`, `entry 0x30100000` | ROM загрузил сегмент в TCM и передаёт управление нашему входу. Длина меняется вместе с бинарём. |
| `P4 rev1.3: ROM -> Rust OK` | Наш Rust-код дошёл до вывода через USB. |
| `rst:0x17 (CHIP_USB_UART_RESET)` | Сброс через USB Serial/JTAG UART control. Наблюдался при управлении портом; не считать автоматически падением прошивки. |
| `rst:0x3 (SW_SYS_RESET)` | Программный сброс цифровой системы; наблюдался во время экспериментов с командой запуска ROM. |
| `rst:0x7 (HP_SYS_HP_WDT_RESET)` | Сброс по MWDT. До исправления flashboot mode сопровождался повторным баннером ROM и одним маркером приложения за цикл. |

В исходном минимальном тесте повторение строки нашего приложения было штатным диагностическим циклом; текущая диагностика touch выдаёт heartbeat и события. Повторение баннера `ESP-ROM`, строки `rst:` и `entry` означает новые запуски. Молчание USB не доказывает зависание CPU: текущий вывод блокируется при заполненном FIFO, а USB может переподключаться.

## Watchdog после ROM

Простого снятия `WDT_EN` оказалось недостаточно: **flashboot mode работает независимо** и продолжал сбрасывать чип.

Ранний код [src/hal/watchdog.rs](../src/hal/watchdog.rs), вызываемый из `rust_main`, выполняет:

| Блок | Регистры | Что делаем |
|---|---|---|
| LP RTC WDT | CONFIG0 `0x50116000`, WPROTECT `0x50116018` | Открываем защиту ключом `0x50D83AA1`, снимаем `WDT_EN` bit 31 и `FLASHBOOT_MOD_EN` bit 12, закрываем защиту. |
| TIMG0 MWDT | CONFIG0 `0x500C2048`, WPROTECT `0x500C2064` | Тот же ключ; снимаем enable bit 31 и flashboot bit 14; устанавливаем **CONF_UPDATE_EN bit 22**, чтобы применить изменения между тактовыми доменами; закрываем защиту. |
| TIMG1 MWDT | CONFIG0 `0x500C3048`, WPROTECT `0x500C3064` | Аналогично TIMG0. |
| Super-watchdog | CONFIG `0x5011601C`, WPROTECT `0x50116020` | Открываем защиту тем же ключом, устанавливаем **SWD_DISABLE bit 30**, закрываем защиту. Это отключение, а не autofeed; autofeed — другой bit 18. |

Отключение выполняется до блокирующего USB-вывода и задержек. Если в будущем watchdog будет включён для приложения, его обслуживание и аварийный сброс нужно реализовать явно.

## Что мешало отладке

- В некоторых последовательностях с `espflash monitor`/USB-сбросом ROM оставался в download. Это наблюдение конкретной сессии, не утверждение, что любая команда espflash всегда оставляет download. Для воспроизводимого запуска добавлен `scripts/monitor.py`.
- Прямой запуск ELF через RAM downloader подтвердил работоспособность кода, но **не подтверждал запуск из flash**. Последний отдельно подтверждён сообщениями `SPI_FAST_FLASH_BOOT`, `load`, `entry` и маркером Rust.
- Унаследованный watchdog мешал следующей записи: одна попытка espflash закончилась `Verification of flash content failed`. Этот промежуточный образ не считался успешно прошитым. Для восстановления сессии watchdog временно отключили через ROM register commands и записали образ с проверкой hash. После исправления runtime обычный `scripts/flash.sh` повторно отработал успешно.
- Временный `setfacl` на `/dev/ttyACM0` пропал после USB-переподключения. Пользователь `kot` добавлен в `uucp`; до нового входа в сессию можно запустить `newgrp uucp` в терминале. Доступ к новому узлу порта после reconnect должен сохраняться через группу.

## Результат и границы проверки

Исходный минимальный образ на момент этой проверки — **368 байт**; текущие модули HAL и их проверки описаны в [hal.md](hal.md). В 35-секундном логе — **48 маркеров и 0 строк `rst:`**. Затем повторно проверены запись штатным скриптом и работа приложения. Это проверка первого запуска, не длительное испытание стабильности.

Логи: `target/boot-physical-reset.log` (вход в Rust и прежний MWDT reset loop), `target/boot-stable-final.log` (35 секунд после исправления), `target/boot-reflash.log` (повторная запись/запуск). `target/` игнорируется Git; ключевые результаты сохранены здесь.

## Возврат голосового ассистента

Первоначальный второй загрузчик по `0x2000` заменён нашим образом. Ранее при экспериментах также менялось начало приложения по `0x10000`. Чтобы вернуть ассистента, восстанавливать полный проверенный дамп по адресу `0x0`, а не только старое приложение. Команда, имена файлов и SHA-256 находятся в локальном [backups/README.md](../backups/README.md). В дамп P4 не входят eFuse и flash ESP32-C6.


## L1-кэш при DMA в SRAM

При запуске CSI обнаружено: отсутствие нашей инициализации кэша не означает,
что ROM выключил L1 DCache внутренней SRAM. DMA доставляет данные, но CPU
без invalidate видит старое содержимое. Для выровненного DMA destination
теперь выполняются L1 writeback+invalidate перед захватом и invalidate после.
MMU/PSRAM для этого не поднимаются. Подробности: [csi.md](csi.md).
