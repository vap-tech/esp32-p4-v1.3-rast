# GT911: кадры касаний и события указателя

Драйвер: [src/devices/gt911.rs](../src/devices/gt911.rs), библиотечный модуль `esp32_p4::devices::gt911`. Использует наш I²C HAL, не зависит от ESP-IDF, аллокатора или RTOS. Разделение: `hal` управляет периферией SoC, `devices` — протоколами внешних устройств.

## Подключение и идентификация

I2C1, SDA GPIO7, SCL GPIO8, 100 кГц, основной 7-битный адрес **0x5D**. INT/RESET не назначаются: драйвер опрашивает контроллер и использует существующую конфигурацию. Общая шина заимствуется только на время обращения; её можно использовать для кодека, RTC и камеры между опросами touch.

На нашей плате прочитано:

```text
GT911 READY addr=0x5d fw=1060 config=99 size=1024x600 max=5
```

Product ID — `39 31 31 00` (`911\0`), firmware — **0x1060**, config version — **99 / 0x63**, размер координатного поля — **1024×600**, maximum contacts — **5**. Альтернативный адрес 0x14 этим драйвером не используется.

| Регистры | Назначение |
|---|---|
| `0x8140…0x8143` | Product ID, проверяется при создании драйвера |
| `0x8144…0x8145` | Firmware version, little-endian |
| `0x8047` | Configuration version |
| `0x8048…0x8049` / `0x804A…0x804B` | X/Y limits, little-endian |
| `0x804C`, младшие 4 бита | Максимальное число контактов |
| `0x814E` | bit 7 — data ready, младшие 4 бита — число контактов |
| `0x814F + 8*n` | Запись контакта: ID (младшие 4 бита), X low/high, Y low/high, size low/high, reserved |

Адрес регистра в I²C prefix передаётся **старшим байтом первым**; числовые поля внутри ответа — **младшим байтом первым**. `size` — сырое поле размера контакта; это не измеренная сила нажатия.

## Чтение и подтверждение

`Gt911::new(&mut bus, &mut timer)` читает ID и конфигурацию. `read_frame()` возвращает:

- `Ok(None)` — нового кадра нет. Это **не отпускание**.
- `Ok(Some(frame))` — свежий кадр, включая кадр с нулём контактов. `frame.points()` возвращает до пяти точек.
- `Err(...)` — ошибка I²C, неверный Product ID при инициализации или некорректный кадр.

Контроллер подтверждается записью **0 в `0x814E`**, только после чтения готового отчёта. Записей в постоянную конфигурацию нет. Кадр на 5 контактов занимает 40 байт; драйвер читает его кусками 32+8 под один data-ready, затем подтверждает. Timestamp — SYSTIMER в момент окончания чтения, до ACK отчёта, а не аппаратная метка GT911.

При ошибке чтения status остаётся pending для повторной попытки. При ошибке подтверждения кадр не передаётся приложению. Количество >5 и повторяющиеся IDs считаются malformed report: он сбрасывается подтверждением, возвращается `InvalidFrame`. Ошибки не создают ложное событие `up`.

## События

`Tracker::update(Option<Frame>)` выдаёт фиксированный массив из двух `Option<Event>`:

- Первый контакт → `down`.
- Изменение X/Y выбранного контакта → `move`.
- Свежий кадр без контактов → один `up` с последними координатами.
- Повтор одинаковой позиции или отсутствие свежего кадра → событий нет.
- Пока выбранный ID присутствует, он сохраняется независимо от порядка записей и появления других пальцев.
- Если выбранный ID исчез, но другие остались: сначала `up` старого, затем `down` нового. Для выбора нового используется минимальный ID.

Это **один основной указатель**, а не полный поток независимых multitouch-событий. Все контакты доступны через `Frame`, если приложению нужны свои жесты. Ни heap, ни очередь переменного размера не используются.

Приложение запрашивает кадры с паузой 10 мс и пишет в USB:

```text
touch down id=0 x=427 y=335 size=... us=...
touch move id=0 x=... y=... size=... us=...
touch up id=0 x=... y=... size=... us=...
touch alive frames=... errors=0 us=...
```

Общий период больше 10 мс из-за I²C и вывода. USB-консоль блокирующая: без читающего хоста её FIFO может остановить дальнейший опрос. Экран/DSI пока не инициализируются; GPIO23 держится low, тест выполняется на тёмном экране.

Координаты возвращаются **сырыми**, без перестановки, инверсии, масштабирования или ограничения диапазона. Размер 1024×600 прочитан из контроллера. После ручного теста пользователь подтвердил совпадение координат с дисплеем. Преобразование координат не понадобилось; это подтверждение пользователя, а не автоматическая калибровка.

## Проверки

Пять host-тестов проверяют:

1. Нажатие → нет свежего кадра → повтор → движение → отпускание; дубли событий не возникают.
2. Сохранение ID при перестановке контактов и порядок `up/down` при смене основного пальца.
3. Byte order, ID mask и размер контакта.
4. Отбрасывание неверных длин, количества и duplicate IDs.
5. Декодирование пяти контактов, включая пятую запись, и выбор основного ID.

```bash
cargo test --lib --target x86_64-unknown-linux-gnu
cargo clippy --release -- -D warnings
cargo fmt --check
```

`build.rs` применяет embedded linker script только к RISC-V target, поэтому библиотечная логика тестируется на компьютере без MMIO. Такие тесты не подтверждают электрическую часть I²C.

Аппаратная проверка: новый образ **8784 байта** записан и запущен напрямую ROM. ID/конфигурация прочитаны; аппаратные касания дают `down/move/up`, подтверждение кадров работает; ошибки I²C/кадров в ходе сеанса не наблюдались. Смена выбранного ID зафиксирована в логе; число одновременных контактов отдельно не логировалось. Аппаратная проверка всех пяти контактов и чтения пятой точки двумя I²C-пакетами пока не выполнена. Сырые логи: `target/touch-first.log`, `target/touch-interactive.log` (игнорируются Git).

## Карта памяти этапа GT911 (история)

Текущая карта с отдельным стеком/аренами и bypass кешей: [memory.md](memory.md).

Начиная с этого этапа 8 КиБ TCM больше не ограничивают весь код:

| Область | Адреса | Содержимое |
|---|---|---|
| HP TCM | `0x30100000…0x30101FFF` | Только `.entry`, `_start` (78 байт в проверенном образе) |
| Низ SRAM | `0x4FF00000…0x4FF1FFFF` (128 КиБ) | `.text` и `.rodata` |
| SRAM data/stack | `0x4FF20000…0x4FF27FFF` (32 КиБ) | `.data`, `.bss`, стек; initial SP `0x4FF28000` |
| ROM shared buffers | С `0x4FF296B8` | Не занимаются нашим linker script |

ROM загружает все инициализированные сегменты непосредственно из единого образа по flash `0x2000`. `_start` включает L2 SRAM clock force-on, выполняет fences, устанавливает стек, обнуляет BSS и вызывает `rust_main`. Программного загрузчика, MMU, кешей и PSRAM в этом пути нет. Linker сохраняет минимум 8 КиБ под стек.

Расположение ниже ROM buffers сверено с локальным `~/esp-idf/components/bootloader/subproject/main/ld/esp32p4/bootloader.memory.ld.in` (ветка rev <3). Базовые GT911 status/point/ACK операции также присутствуют в старых `old/esp-32-p4-v1.3/main/touch_gt911.c` и `old/esp32-p4-voice-device/main/voice_device.c`; код новой реализации написан на Rust и работает поверх нашего HAL.

Итог ручного сеанса: 151 `down`, 413 `move`, 151 `up`; все нажатия завершены, порядок событий и диапазон координат проверены скриптом. Сводка — `target/touch-check.json`. Последний heartbeat: 22948 кадров, 0 ошибок. После сеанса пользователь подтвердил, что координаты совпадали с дисплеем.
