# HP0 ↔ HP1: очереди и уведомления

## Архитектура

Ядра имеют фиксированные роли и отдельные рабочие области/стеки. Каждый
драйвер и каждый изменяемый буфер имеют одного владельца. Нет общего
планировщика, миграции задач или общего конкурентного аллокатора.

Первая схема: очередь заданий HP0→HP1 и очередь результатов HP1→HP0.
HP1 не получает файловую систему, USB-консоль, SDMMC, сетевые драйверы или
объекты аллокаторов HP0. Пока задания содержат только целочисленные данные;
никаких моделей или обработки реального медиапотока здесь ещё нет.

## Очередь

`src/intercore.rs`: `Queue<T, N>` с единственным producer и consumer.

- `split(&mut self)` выдаёт ровно одну пару endpoints; они не Clone/Sync.
- Между ядрами передаются только значения `T: Send`, `Sync` не требуется.
- `try_push` перемещает значение. При заполнении возвращает исходный `T`:
  вызывающий решает, повторить попытку, отложить или отменить задание.
- `try_pop` передаёт владение потребителю; все N слотов доступны.
- Оставшиеся значения уничтожаются при уничтожении самой очереди.
- N — степень двойки, минимум 2. Индексы wrapping, выбор слота через маску.
- Никаких аллокаций или блокировок; Release/Acquire публикуют слот и его
  освобождение. Они не выполняют обслуживание аппаратных кешей.

Сначала размещаем очереди, endpoints HP1 и status в SRAM и используем только
некешируемый alias `0x8ff...` на обоих ядрах. Прямого параллельного доступа
к тому же объекту через кешируемый alias нет. Указатель на буфер в сообщении
сам по себе не обеспечивает когерентность содержимого этого буфера.

Существующие объекты памяти, ссылающиеся на локальный Arena с Cell/RefCell,
нельзя объявлять Send ради удобства. Для больших буферов понадобится
отдельный проверенный контракт передачи/возврата либо собственная арена HP1.

## Аппаратное уведомление

`src/hal/multicore.rs`: старт/парковка HP1 и FROM_CPU sources.

В лабораторном протоколе:

| Направление | Источник | Регистр уровня | Матрица получателя | CPU IRQ |
|---|---|---|---|---|
| HP0→HP1 | FROM_CPU0 | `0x500e5010` | `0x500d693c` | 18 |
| HP1→HP0 | FROM_CPU1 | `0x500e5014` | `0x500d6140` | 18 |

Это два уровня, а не аппаратные очереди и не счётчики сообщений.
Публикация нескольких заданий может дать одно прерывание. Уведомлять нужно
после публикации данных; ISR сбрасывает уровень до обработки очереди.
Истина — содержимое очередей. Счётчик IRQ не обязан совпадать с числом задач.

В диагностическом ISR сохраняются только используемые t0/t1/t2, проверяется
mcause, сбрасывается свой FROM_CPU level и увеличивается счётчик.
Вызовов Rust, FP/PIE, аллокаций и работы с периферией приложения в ISR нет.
Неожиданный IRQ/exception фиксирует mcause/mepc/mtval и останавливает тест.
Это отдельный boot-time IRQ-контекст, не расширение действующего SD ISR.

## Гонка пустой очереди и WFI

Недостаточно проверить очередь и затем вызвать WFI: уведомление может прийти
и быть обработано между этими действиями, оставив ядро спать с готовой работой.

`multicore::wait_if` временно снимает глобальный MIE, повторно проверяет
предикат пустоты, при необходимости выполняет WFI, затем восстанавливает MIE.
Локальная CLIC-линия остаётся включённой. Pending level должен будить ядро
при MIE=0; ISR не может сбросить его между повторной проверкой и WFI.
После любого пробуждения очередь проверяется снова, ложные пробуждения допустимы.

Поведение подтверждено на CLIC P4 rev1.3 серией аппаратных прогонов, включая
сотни входов в WFI за прогон и повторные сбросы. Это проверка данной схемы,
а не доказательство корректности любого IRQ-протокола.
`wait_if` нельзя применять к произвольному источнику без такого контракта.

## Лабораторные образы

Без кешей: `./scripts/image.sh --features multicore-queue-lab`.
С L1 I0+I1+D ON: `./scripts/image.sh --features multicore-cache-lab`.
Во втором варианте L2=0, переключения кешей происходят только до запуска
HP1 и после подтверждённой парковки. Для I1 добавлен отдельный выбор
ядра в `hal::memory::set_instruction_cache_for`; I0 API сохранён.
Флаг подразумевает `multicore-lab`, но заменяет старую однослотовую пробу,
чтобы не пытаться запустить уже припаркованное ядро повторно.
Обычная сборка эти boot-time тесты не выполняет.

`src/multicore_queue_lab.rs`:

- отдельный статический стек HP1 8 КиБ;
- две очереди по 8 сообщений, некешируемые shared objects;
- 4096 нумерованных заданий с проверкой результатов и порядка на HP0;
- пакетная подача, заполнение очередей, паузы для входа HP1 в WFI;
- IRQ18 на обоих ядрах, счётчики уведомлений;
- остановка отдельным заданием и подтверждение парковки;
- восстановление прежнего IRQ-контекста HP0 до продолжения обычного boot.

Успех на железе потребует 4096/4096, правильного порядка/значений,
ненулевых IRQ-счётчиков обоих ядер, `parked=true`, целого stack guard и
отсутствия исключений. Если парковка не подтверждена, продолжение boot и
переключение кешей запрещены: тест печатает ошибку и ждёт reset.
Стек/очереди/переданные endpoints не освобождаются даже при timeout.

После уточнения пользователя (он работает с эмулятором) оба образа прошиты
и проверены на плате. Результаты ниже. Передача изменяемых кешируемых
буферов и конкурентные DMA этими boot-time тестами не проверяются.

## Проверки на ноуте

109 Rust lib tests: FIFO/backpressure, переход счётчиков через usize::MAX,
сохранение pending при повторном split, возврат владения и корректное
уничтожение некопируемых объектов, передача Send/!Sync значения,
100000 сообщений между двумя OS-потоками с проверкой порядка и данных.
Целевой образ собирается для `riscv32imafc-unknown-none-elf`;
Clippy проверяет диагностическую конфигурацию.

Источники регистров — локальный IDF v6.1:
`components/soc/esp32p4/register/hw_ver1/soc/`:
`hp_system_reg.h`, `interrupt_core0_reg.h`, `interrupt_core1_reg.h`,
`reg_base.h`. Начальные аппаратные результаты: [cpu-bringup.md](cpu-bringup.md).


## Аппаратная проверка, 2026-11-14

CPU около 160 МГц, L2=0; все очереди/ports/status и стек HP1 — uncached SRAM.

| Режим | Прогоны | Заданий за прогон | IRQ HP0 | IRQ HP1 | WFI HP1 | Результат |
|---|---:|---:|---:|---:|---:|---|
| L1 bypass, первоначальная подача | 1 | 4096 | 4097 | 9899 | 434 | PASS |
| L1 bypass, уведомление только при новой публикации | 1 | 4096 | 4097 | 1019 | 441 | PASS |
| I0+I1+D ON, уведомление только при новой публикации | 3 | 4096 | 4097 | 1185 | 417 | PASS во всех |

Последние два cached прогона — повторные сбросы через espflash без
перепрошивки. Полное снятие питания в этом этапе не проверялось.
Во всех прогонах правильные значения и порядок, stop/park подтверждены,
stack guard цел, trap=0; после восстановления IRQ и кешей стартует web.
L1 bypass register в cached тесте =0, в bypass тесте =0x13; L2 bypass=0x20.
Количество IRQ может зависеть от таймингов; числовое совпадение счётчиков
в трёх cached прогонах не является требованием протокола.

Первая версия сигнализировала даже при неудачной попытке добавить новое
задание в полную очередь. Это давало лишние IRQ. Исправлено: HP0 уведомляет
только после фактической публикации хотя бы одного нового сообщения.
Очередь остаётся источником истины; прерывание не подтверждает потребление.

Артефакты локально: `target/cpu-bringup/queue/{bypass,cached}/`, образы,
ELF и логи отдельных запусков. Первый прогон: `queue/boot-1.log`.

## Следующий этап после boot probe (исторический план)

HP1 по-прежнему паркуется до запуска обычных драйверов. Постоянная работа
HP1 рядом с web потребует интеграции IRQ18 в runtime, сохранения маршрута
при scoped SD IRQ и протокола остановки обоих ядер перед общим обслуживанием
кешей. Нельзя просто оставить boot worker активным: существующие процедуры
cache maintenance требуют единственного активного владельца.

Роли драйверов не менялись, D-cache в штатном web остаётся OFF.
Одновременный LCD/SD/I2S с работающим HP1 — отдельная следующая проверка.

После испытаний возвращена обычная сборка без multicore labs. Web READY,
GET `/api/net-test?bytes=4194304` побайтно совпал с эталоном, POST принял
4194304 байта, корневая страница отдаётся HTTP200 (40694 байта). Файлы SD
этим завершающим RAM-only тестом не создавались/не изменялись.

Постоянный worker и интеграция IRQ реализованы следующим этапом:
[hp-worker.md](hp-worker.md). Ограничения boot probe выше не описывают
нынешний штатный runtime.
