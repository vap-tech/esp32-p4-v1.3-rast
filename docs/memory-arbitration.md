# PSRAM, LCD и арбитраж: измерения rev1.3

Исследование на подключённой плате, 2026-11-12. Штатный способ рисования
сохранён: packed u32, `fence rw,rw` и пауза 320 тактов каждые 32 пикселя.
Пользователь подтвердил отсутствие вспышек с этим исправлением.
Экспериментальные настройки автоматически возвращаются после прогона.

## Тракт и доступные механизмы

CPU → H2X (AHB/AXI bridge) → AXI Matrix → MSPI → PSRAM.
LCD читает PSRAM через DW-GDMA, затем передаёт данные в MIPI DSI bridge FIFO.
Это независимые инициаторы запросов, но общие контроллер и физическая память.
Underrun означает, что FIFO не получил пиксели вовремя; корректное содержимое
framebuffer само по себе не гарантирует непрерывную выдачу пикселей.

| Уровень | Механизм | Что установлено |
| --- | --- | --- |
| AXI Matrix | ARQoS/AWQoS и приоритет мастера | Документированы; LCD read QoS/prio=15 проверены |
| AXI Matrix | Регулятор burstiness, peak/transaction rate | Есть API в IDF; здесь чтение настроек отвергается |
| CPU H2X | Post-write и cut-through | По умолчанию оба включены; раздельное отключение проверено |
| DW-GDMA | Приоритет канала, burst, outstanding | Приоритет регулирует конкуренцию каналов самого DMA; не является глобальным приоритетом PSRAM |
| DSI bridge | FIFO, credit, low-water/request burst | Сняты фактические значения; live-перенастройка не выполнялась |
| MSPI | Частота, read/write splice, fast-write | Сняты значения; в этих опытах не менялись |
| ПО | Ширина записей, ограничение непрерывной серии | Рабочее исправление проверено пользователем и счётчиками |

Снятая конфигурация: CPU160 МГц, PSRAM80 МГц DDR x16, L2 bypass,
I/D-cache bypass. CPU alias PSRAM `0x88000000`, DMA alias `0x48000000`.
Framebuffer начинается с offset128. У LCD source SMS=1: второй AXI master
DW-GDMA (SDK master ID6; TRM нумерует порты с единицы, это порт7).
Матрица изначально имеет нулевые QoS/priority. Канал LCD имеет priority5,
source outstanding8, destination4, source burst512 элементов по8 байт,
read ARLEN16 beats. Bridge: request burst256, credit threshold1024,
credit burst800, low-water768; размер физического FIFO только из этих
порогов не утверждаем. CPU H2X `0x500e5138=3`.

## Воспроизводимый тест

```sh
python3 scripts/display-control.py --arbitration status --hold 0
python3 scripts/display-control.py --arbitration 'bench baseline u32 frame 40' --hold 0
python3 scripts/display-control.py --arbitration 'bench postwrite-off u32 frame 200' --hold 0
```

Только при активном LCD, отключённых камере/будильнике, свободных аренах,
D-cache OFF и L2 bypass. Прямоугольник400×88 в (312,480):70400 байт.
Сначала сохраняется его содержимое в SRAM. Каждый повтор записывает цвет,
проверяет все пиксели чтением и делает паузу с меняющейся фазой относительно
scanout. После теста возвращаются настройки и исходные пиксели, проверяются
защитные области. ESC останавливает тест между повторами.

`frame` пишет в активный framebuffer; `scratch` — в отдельную арену PSRAM
от4 МиБ с тем же шагом строк2048 байт и тем же смещением внутри4-КиБ страницы;
`linear` использует непрерывные строки в этой арене. `u16/u32` — без пауз,
`paced` — с рабочими паузами. Данные SD не изменяются.

`underrun_samples` — число проверок с установленным sticky-флагом, а не число
пропущенных пикселей/кадров. Проверки выполняются после всей серии записей и
после проверки/паузы; чтения MMIO между строками могли бы скрыть проблему.
`min_fifo` — минимум в точках выборки, не непрерывный аппаратный минимум.
`write_total_us` включает только запись, без проверки, ожидания и восстановления.

затрагивает агрегированный CPU/AHB путь, где находятся также другие мастера;
нужны отдельные SD/EMAC/I2S и смешанные длительные испытания. Штатная политика
остаётся прежней, post-write возвращается к3 вместе с cut-through после опыта.

## Что объяснено, а что пока нет

Прямо подтверждён LCD underrun во время некоторых CPU-записей в активный
framebuffer. Повышение приоритета в матрице его не устранило. Паузы устраняют
наблюдавшиеся срывы; сочетание post-write OFF и u32 тоже прошло этот тест.

Но **объяснение только суммарной пропускной способностью недостаточно**:
аналогичная запись вне активного framebuffer не вызывает срыв, даже с теми же
stride и page alignment. Возможны зависимости чтение/запись по адресам,
очереди контроллера и планирование транзакций. Они ещё не разделены опытами.
Нельзя называть точную причину доказанной или считать одни приоритеты решением.
Нулевая статистика короткой серии не означает гарантированное отсутствие
срывов при любой нагрузке. Это также не проверка tearing при обновлении одного
framebuffer: старый/новый кадр может смешиваться без underrun.

## Ограничения ревизии и опасные места

* Запись в candidate channel AXI_QOS `0x50081258` из hw_ver1 заголовка IDF
  приводила к зависанию/потере управления даже при записи сохранённого нуля.
  В доступной TRM rev1.3 регистр не описан. Профиль удалён; чтение работает.
  Причина зависания не установлена, переносить поля нового железа вслепую нельзя.
* QoS HWCFG=`0x0070d151`:13 masters,7 slaves, BI_DIR_CMD_EN=0.
  Пробная indirect read-команда получила CMD_ERR. Теперь диагностический код
  проверяет HWCFG и не посылает неподдерживаемые чтения. SDK содержит write API
  token bucket, но включать его без сохранения исходных настроек в этом тесте
  не стали. Наличие SDK API не подтверждает восстановимое чтение на нашем чипе.
* Параметры DMA/FIFO требуют отдельной процедуры остановки и перезапуска.
  Частота PSRAM не повышалась, MSPI splice/fast-write не менялись.
* Опыты не выполнялись с D-cache ON. Они не заменяют проверку когерентности DMA.

Следующие различающие опыты: перенести источник LCD в другую область PSRAM и
проверить, следует ли проблема за активным framebuffer; затем проверять burst/
outstanding/FIFO через остановку канала. После этого — смешанная нагрузка и
длительный прогон перспективного post-write OFF + u32. Сначала объяснить
адресную зависимость, затем выбирать постоянную аппаратную политику.

## Быстрая проверка H2X BUSY, 2026-11-12

`HP_SYSTEM_CPU_ICM_H2X_BRIDGE_BUSY`, bit2 регистра `0x500e5138`,
в локальном IDF v6.1 встречается только в описаниях регистров, без использования
в коде компонентов и без пояснения (`need_des`). Добавлены лабораторные режимы
`probe` (однократное чтение), `busy` (ожидание0), `fence-busy` (fence + ожидание).
Проверка каждые32 пикселя, ожидание ограничено160000 тактами; при таймауте
тест прекращается с восстановлением регистров и картинки.

Одна финальная сборка, по40 повторов того же прямоугольника:

| Режим | BUSY при первом чтении | Дополнительных опросов | Underrun samples | Запись всего, мс |
| --- | ---: | ---: | ---: | ---: |
| u16 контроль | — | — | 19 | 446,753 |
| u32 контроль | — | — | 0 | 316,606 |
| probe | 1 | 0 | 0 | 740,250 |
| busy | 9336 | 17099 | 0 | 345,713 |
| fence-busy | 9105 | 10648 | 0 | 345,205 |
| paced | — | — | 0 | 388,723 |

Во всех случаях данные/guards совпали, таймаутов нет. Максимальное измеренное
время одного участка опроса245/246 тактов (примерно1,54 мкс); сюда входят
чтение счётчика и MMIO, это не точная длительность транзакции PSRAM.
Флаг динамический: наблюдали1 и последующий0. `fence` перед опросом не
устраняет BUSY. Это не доказывает завершение записи в физическую PSRAM:
подтверждена только наблюдаемая занятость моста.

Добавление инструментирования изменило машинный код/скорость контрольного
u32-цикла: прежний тест писал около229 мс, новый317 мс и тоже перестал
воспроизводить underrun. Поэтому нули busy/fence-busy нельзя трактовать как
доказательство исправления именно ожиданием. Даже одно чтение MMIO меняет
нагрузку и темп. Штатный framebuffer по-прежнему использует прежние паузы;
BUSY не включён в его рабочий путь. Логи `busy-final-*.log` находятся в
игнорируемом `target/memory-arbitration/`.

### Визуальная проверка пользователя после BUSY-тестов

Пользователь сообщил о многочисленных белых вспышках во втором тесте;
белых вспышек не было только на предыдущем замере. Точный режим по этому
наблюдению не сопоставлен. Следовательно, нулевая статистика приведённых
выборок НЕ подтверждает отсутствие видимых срывов за весь запуск.
Подготовка, интервал до очистки sticky-флага и восстановление картинки
не входят в underrun_samples. Это возможные слепые зоны, но происхождение
увиденных вспышек ими пока не доказано. Режимы BUSY не считаются визуально
проверенными или безопасной заменой штатных пауз. Нужен учёт всего жизненного
цикла теста и по одному явно обозначенному режиму за запуск.
