# DMA validation: SD, LCD, I2S and mixed load

2026-11-06, ESP32-P4 rev1.3. Продолжение стабильной базы 9afb4d1.
Целевая конфигурация тестов: **L1 I+D ON, L2=0, PSRAM uncached**, около 160 MHz.
Автоматическая загрузка остаётся all-bypass; переключение — явными командами.
Новые зависимости, RTOS, heap и обработчики прерываний не добавлены.
Камера не запускалась и её код не менялся.

## SD: грязный RX и границы пользовательских срезов

`:sd-stress` / `--sd-stress`, активный framebuffer, камера выключена.
Один прогон: 64 rounds × 3 LBA × 4 lengths × 6 offsets = **4608 чтений**.

- LBA: 0, 2048 и последние 16 секторов карты.
- Размеры: 512, 1024, 4096, 8192 B; CMD17/CMD18, включая оба DMA-дескриптора.
- Смещения пользовательского среза: 0, 1, 3, 31, 63, 65 B относительно начала
  рабочей области с дополнительным защитным префиксом 64 B.
- Эталон каждого диапазона отдельно собран из 16 обычных односекторных чтений.
- `Sdmmc::read_poisoned` сначала публикует физические canaries во всём bounce-buffer,
  затем записывает другой шаблон только в RX-диапазон. Через uncached SRAM alias
  проверяется, что физическое слово отличается от грязной CPU cache line.
- Используется обычный production `read_sectors`: pre writeback+invalidate,
  post invalidate. Пользовательский буфер не передаётся аппаратуре: DMA работает
  только с выровненным 8192 B bounce-buffer и отдельными 64 B descriptor lines.
- Данные сравниваются побайтно. Проверяется prefix/suffix пользовательского среза
  и физический хвост DMA-буфера за длиной RX (через uncached alias).
- Временные reference/workspace (33024 B) берутся из пустой SRAM arena; после
  возврата всех заимствований арена сбрасывается, повторные запуски не расходуют RAM.

Первый прогон + 10 повторов: **50688 чтений**, во всех 50688 подтверждены dirty
lines, сравнения/canaries пройдены. 10 повторов заняли **67.128 s**, около 6.6 s
на 4608 случаев. LCD постоянно выполнял scanout. Карта не записывалась.
Логи target/dma-stress/{sd-first,sd-soak}.log. Ранние результаты относятся к
первому диагностическому образу; финальная регрессия записана отдельно.

Это проверка допустимых sector-sized RX. Частичные cache lines пользовательского
среза обрабатываются CPU-копированием; аппаратуре не передаётся частичная линия.
Это не проверка произвольного байтового размера SDMMC DMA и не тест SD-записи.

## LCD при обновлениях

8 серий `--jpeg-idct-bench` = **32 полных кадра за 77.896 s**. SD читает JPEG,
CPU записывает uncached framebuffer, LCD сканирует его одновременно. У обоих
IDCT совпали stream/full-frame hashes, framebuffer/stack guards целы.
Лог target/dma-stress/lcd-jpeg-soak.log.

Tearing, оптическое качество и каждый физически выведенный кадр этим тестом
не измерялись. Один framebuffer допускает разрыв кадра во время записи; это
не следует путать с порчей данных из-за некогерентного кеша.

## I2S: исправление кольца и проверка отказа

Раньше ring из двух блоков по 512 stereo frames выдавал done+descriptor error
на первом возврате по циклу. Header/адреса обоих descriptors читались из физической
памяти: второй ещё имел OWN=DMA. Проверены варианты:

- сброс канала после priming не устранил ошибку;
- отключение descriptor burst и смена EOF mode не устранили ошибку;
- конечная цепь из двух блоков штатно отработала и остановилась;
- отключение owner check позволило короткий поток, но этот диагностический режим
  **удалён**, поскольку не обеспечивает аппаратную остановку при нехватке данных;
- **четыре блока с исходными owner check, burst, EOF mode и auto-writeback**
  обеспечили непрерывное воспроизведение.

Рабочий ring: **4 × 2048 B = 8192 B**, 128 ms PCM при 16 kHz, stereo PCM16 slots.
Это экспериментально подтверждённая достаточная глубина для текущего режима.
Результаты указывают на недостаточную глубину старого кольца относительно
выборки DMA/FIFO; точное число внутренних стадий prefetch этим не установлено.

Все data/descriptor lines изолированы по 64 B. CPU читает/публикует OWN только
через uncached SRAM alias. Данные копируются только в освобождённый блок;
двойной writeback+invalidate и fence завершаются до публикации OWN=DMA.
Указатели цепочки после старта не меняются. Descriptor snapshot теперь читает
первые три слова каждого дескриптора через uncached alias, а не устаревший кеш.

`stream_released` / `stream_refill_now` позволяют поллинг из обычного event loop
без заимствования SYSTIMER, которым в это время владеет SD file. Cache maintenance
имеет watchdog 16M CPU cycles (около 100 ms при измеренных 160 MHz). Старые
методы с Timer сохранены как wrappers. Глобальных callback pointers нет.

WAV с SD при активном LCD: **60 s, 1872 refills**, max_refill **2179 us**, raw DMA=3
(done+EOF, без error), штатная остановка PA=false. Лог audio-lcd-60s.log.
После перехода к timerless service дополнительно проверяется финальная сборка.
Это проверка цифрового потока и завершений DMA; независимая оценка звука
слушателем/аналоговым измерением в этом заходе не проводилась.

`:play-stall SATIE.WAV` / `--play-stall`: намеренная пауза producer **200 ms**.
Получены owner descriptor error, PARK=1, OWN=CPU у всех четырёх блоков; после
обнаружения ошибки codec muted, PA=false, канал остановлен. Следующий обычный
запуск WAV прошёл. Аппаратура останавливает выборку вместо повторного чтения
старого PCM. Автоматического продолжения того же файла после underrun пока нет:
ошибка возвращается вызывающему коду, повторная команда заново инициализирует TX.
Логи audio-underrun.log и after-underrun-recovery.log.

## Смешанный прогон

`:mixed-stress` / `--mixed-stress` выполняет **20 JPEG HOME.JPG** с SD, Loeffler,
CPU writes → PSRAM framebuffer → LCD scanout. Параллельно GDMA-AHB передаёт
синтезированный PCM с изменяемым generation tag; producer обслуживается между
выходными строками MCU и перед открытием очередного JPEG.

Это обычные последовательные вызовы, без IRQ/runtime. `AudioWork` владеет Tx,
512-frame scratch и индексом кольца; callback рендера временно заимствует его.
SD и I2S используют разные DMA-контроллеры; cache maintenance выполняется
последовательно. Timer не переинициализируется и не заимствуется через raw aliases.

Первый прогон: **34.920159 s, 1095 refills**, max service gap **31.375 ms**,
BCK=17879121, DMA raw=3, 20 hashes **534b3012**, guards=true.
Stack high-water **14508 / 16384 B**, нижние 64 B целы. PA выключен на всём тесте.
Сравниваются скорость BCK с 512 kHz (допуск 1%), число пополнений с 31.25 block/s,
ошибки DMA и интервал обслуживания с выбранным бюджетом 64 ms.

Проверяется цифровой PCM transport при SD JPEG + LCD. Это не одновременное чтение
двух файлов FAT32 и не музыка с SD во время JPEG: музыкальное SD-воспроизведение
проверено отдельно, здесь источник PCM — CPU. PCM GPIO/аналоговый сигнал под
смешанной нагрузкой внешним прибором не захватывался.

## Размещение памяти

Для четырёх блоков понадобились дополнительные 4096 B data и 128 B descriptors.
Старый статический SD_PROBE_BUFFER 8192 B удалён: синхронные legacy SD diagnostics
переиспользуют **бывший загрузочный стек 4FF26000…4FF27FFF** после перехода CPU
на верхний runtime stack. Перед созданием Rust slice все байты инициализируются.
Вызовы не реентерабельны; не допускаются параллельно с boot или ISR. Этот scratch
не используется как аппаратный DMA target, SD по-прежнему имеет свой bounce-buffer.

Текущая карта нижней SRAM:

| Регион | Назначение |
| --- | --- |
| 4FF00000…4FF20FFF (132 KiB) | CODE/rodata budget |
| 4FF21000…4FF25FFF (20 KiB) | DATA/BSS/boot audit, linker reserves headroom |
| 4FF26000…4FF27FFF (8 KiB) | boot stack → runtime legacy SD scratch |
| 4FF28000…4FF3FFFF | сохранённая ROM область |

Линкер проверяет положение scratch и минимум 8192 B boot stack. Верхняя арена
**496 KiB**, runtime stack **16 KiB**, PSRAM-размещение не изменились. В сборке
l2-128 верхняя арена остаётся 368 KiB с соответствующим стеком; low layout общий.
Длинная legacy-справка вынесена в [console.md](console.md), команды сохранены.

## Повторение

```sh
./scripts/flash.sh
python3 scripts/display-control.py --icache on --dcache on --image HOME.JPG
python3 scripts/display-control.py --sd-stress
python3 scripts/display-control.py --mixed-stress
python3 scripts/display-control.py --play SATIE.WAV --seconds 60
python3 scripts/display-control.py --play-stall SATIE.WAV
python3 scripts/display-control.py --play SATIE.WAV --seconds 3
python3 scripts/display-control.py --dcache off --memory --clock
```

После reset — all-bypass. Generic typed AhbDmaBuffer при D-cache ON по-прежнему
отказывает: проверенные SD/I2S клиенты пока используют собственные корректные
handoffs. CSI/ISP и универсальная реализация typed DMA остаются отдельной работой.
Выводы о бесконечном uptime или всех возможных режимах DMA из этих прогонов не делаются.

Финальный default образ **141616 B**, SHA256
`fce90cf41483bac631a9aa2e7cb5ae4b2f5e51a1ccd9dbf9ae4ab8f746744c8c`.
Финальная регрессия — target/dma-stress/final-*.log; аппаратные тесты default
образа, l2-128 повторно проверяется сборкой. Логи исходных экспериментов сохранены.

Финальная регрессия прошла полностью за **111.212 s**: ещё 4608 dirty RX reads
(итого **55296**), смешанный прогон **34.992849 s / 1097 refills / max gap
31.378 ms**, underrun, затем WAV **60 s / 1872 refills / max 2200 us**, повторный
полный JPEG benchmark. Все guards целы; mixed stack peak **14508 B**.
После окончания I ON / D OFF, L2=0, PA выключен. 37 host tests в каждой feature
сборке, оба release builds, clippy -D warnings, fmt и Python syntax прошли.

Legacy Z/FAT32 и m/multi-sector probes также прошли с D-cache ON после переноса
scratch: повторные чтения совпали; m checksum f8a18494 для 1/2/8/16 секторов.
После них снова D-cache OFF, stack guard цел, arena used=0/high_water=33024 B.

## Контракт retired boot stack

8 KiB scratch разрешён только после последнего startup-перехода SP на `_stack_top`.
Существующие обращения SP к `_boot_stack_top` находятся только в startup assembly;
trap не переключается обратно на этот стек. Ни IRQ, ни другой CPU не могут получить
эту область под стек во время runtime SD diagnostics. Сейчас machine interrupts
выключены, CPU1 не запущен. Перед каждым заимствованием scratch полностью
инициализируется, ссылки не сохраняются после синхронной команды.

Linker ASSERT фиксирует scratch start=4FF26000, а `_boot_static_end` обязан быть
не выше этой границы: BSS/boot audit не пересекаются с scratch. CODE имеет отдельный
ограниченный регион; верхние runtime stack/arena физически отделены. Перед добавлением
ISR или повторного входа в bootstrap этот контракт требуется пересмотреть.

Измеренный остаток runtime stack: **16384 − 14508 = 1876 B**, включая 64 B нижнего
canary. Это результат конкретного JPEG/нагрузки при выключенных IRQ, не бюджет для
будущих ISR или всех допустимых JPEG. Перед ISR рассмотреть увеличение стека либо
перенос 2 KiB PCM producer scratch из call stack в отдельную SRAM allocation.

## Следующий эксперимент: запас кольца и последовательность реального WAV

Четыре блока сохраняются. Достаточность этого кольца для пройденных тестов
подтверждена; точная первопричина отказа двух блоков **не доказана**. Проверять
содержимое PCM необходимо отдельно от отсутствия descriptor errors.

План, ещё не реализован и не выполнен:

1. Длительная нагрузка **I ON / D OFF / L2=0**: SD JPEG + LCD + реальный WAV,
   затем тот же сценарий с D-cache ON. Нынешний смешанный тест использует
   синтетический PCM; два одновременных потока FAT32 пока не реализованы.
2. Low-watermark кольца. Не называть число `OWN=1` гарантированным временем
   звучания: оно включает текущие/предвыбранные DMA blocks и не описывает FIFO.
   Разделять готовые данные producer, DMA-owned и освобождённые blocks; отдельно
   хранить наблюдаемый `min_ready_blocks`/`min_dma_owned_blocks` с точным определением.
3. `max_refill_latency`: время **от освобождения до публикации OWN**, а не только
   длительность копирования. При polling момент освобождения неизвестен точно:
   `publish − first_observed_free` — нижняя оценка, `publish − last_observed_owned`
   — верхняя. Сохранять обе и не выдавать наблюдаемую задержку за аппаратную точную.
4. `underrun_count`: считать один переход в underrun за инцидент, не каждый
   повторный опрос sticky IRQ. Отдельно считать остановки/перезапуски и ошибки DMA.
5. Цифровой захват I2S и сравнение последовательности с эталонным WAV/маркированным
   PCM: искать пропуски, повторы, неверные каналы и sample order. FIFO tail учитывать
   при сопоставлении, но не ждать его опустошения для возврата уже прочитанной RAM.
6. Слушатель/аналоговое измерение подтверждает тракт DAC/PA. Цифровые счётчики,
   BCK и успешное завершение DMA не заменяют эту проверку.

Метрики и цифровой capture должны быть проверены в том числе искусственной
задержкой producer; их overhead измеряется отдельно. Конечные тесты не дают
гарантии минимального аудиозапаса для произвольной будущей нагрузки.
