# PIE для Ethernet: A/B/A — 2026-11-15

Экспериментальный feature `ethernet-pie` использует128-битное копирование
на HP0 в существующем EMAC driver. Это ускорение CPU-части сетевого тракта,
не смена SD mode/частоты, TCP window, DMA или конфигурации кеша.

## Контракт

`CopyEngine` эксклюзивно владеет PIE-состоянием HP0 от `Emac::start()` до Drop.
Он `!Send + !Sync`, проверяет hart0/PIE OFF/D-cache OFF/L2=0 и не скрывает
чужое состояние: при занятом PIE запуск отвергается. ISR HP0 не используют
Q/PIE, HP1 имеет собственные регистры и продолжает выполнять свою работу.
Drop сначала останавливает EMAC DMA по прежнему протоколу, затем освобождает
память и выключает PIE. Функции копирования не маскируют прерывания.

* DMA ring/OWN/error checks, fences и сроки жизни storage не изменены.
* Путь использует обычную SRAM `0x4ff…`; alias не преобразуется автоматически.
* CPU-owned frame остаётся недоступным DMA во время копирования. RX: после
  проверки OWN и fence, перед возвратом OWN. TX: после возврата OWN, до
  публикации нового OWN и TX doorbell.
* 16-байтное выравнивание проверяется для обеих сторон. Копируются только
  полные16-байтные блоки; начало не округляется вниз, конец — вверх.
* Пакеты<64B, невыравненные указатели, неподдержанные области памяти и хвост
  до15B идут прежним scalar/volatile путём.
* Оpaque assembly call выполняет реальные load/store128 и не эквивалентен
  замене volatile на оптимизируемый Rust memcpy. Барьеры владения сохранены.
* RX/TX CPU workspaces `Network` имеют alignment16 **в обеих A/B сборках**,
  чтобы сравнение не приписывало изменение их раскладки самому SIMD.

Перед запуском DMA вариант PIE проверяет288 комбинаций длины/смещения в обоих
направлениях на трёх свежих frame slots из выделенной EMAC SRAM. Проверяются
содержимое и нетронутые байты вокруг. Длины0..1514, смещения0..15, переходы
15/16/17,63/64/65,511/512/513. Дополнительный постоянный scratch не выделяется.
При несовпадении старт возвращает Error::Pie; при hardware trap сохранять лог
и делать reset. Не считать сеть запущенной после ошибки self-test.

## Почему это помогает SD через веб

SD уже пишет крупные блоки прямым DMA из PSRAM ring. Этот путь и CPU→PSRAM
копирование с защитными паузами для LCD не менялись. GET с SD также использует
прежний bounce buffer и HTTP scratch.

Ускоряется этап Ethernet frame↔CPU SRAM, который присутствует и в RAM-only,
и в HTTP↔SD. Поэтому улучшение скорости загрузки файла не означает, что
ускорилась сама карта или её физический интерфейс. PIE из PSRAM этим
экспериментом не проверяется. Холодные assets/файлы и настройки ФС не менялись.

## Воспроизведение

```sh
# A: контроль, scalar frame copy
./scripts/image.sh
# B: всё то же, PIE frame copy
./scripts/image.sh --features ethernet-pie
# В обоих случаях прошивать target/firmware.bin по0x2000.

python3 scripts/benchmark-ram.py --rounds 7 --output /tmp/ram.json
python3 scripts/benchmark-upload.py --size-mib 32 --output /tmp/sd.json
```

RAM script исключает первый warmup GET/POST, чередует порядок направлений,
проверяет весь GET byte pattern и подтверждённое число POST bytes. POST RAM
не проверяет application-level checksum; полный readback обеспечивает SD test.
SD script создаёт только уникальный свой файл, сравнивает весь readback,
удаляет файл и проверяет неизменность root.

Порядок с прошивкой отдельных фиксированных образов: A1 → B → A2.
CPU160MHz, I0/I1 ON, D OFF, L2=0, проводной100/full, один и тот же ноут/порт,
TCP/HTTP/SD/FAT настройки и PSRAM ring одинаковы. По7 измеренных RAM пар и
по2 полных32-МиБ PUT/GET для каждой прошивки. Xorshift нагрузка выключена
во время сравнения; отдельный SMP stress описан ниже.

`EMAC NET` показывает прежние counters:
`(rx_poll,rx_frames,rx_copy_us,tx_frames,tx_copy_us,tx_wait_us)`.
`EMAC COPY` дополнительно печатает
`(rx_vector_bytes,tx_vector_bytes,rx_scalar_bytes,tx_scalar_bytes,last_rx_ptr,last_tx_ptr)`
в hex. Векторные байты должны быть ненулевыми: иначе измеряется fallback.
Counters сбрасываются перед каждым RAM-only запросом. Первые входные кадры
HTTP могут уже быть приняты до reset; это не полный wire byte counter.

## Дополнительная корректность

В варианте B прошли22 размера файлов0..65539B, включая нечётные/граничные
длины, и3 параллельных PUT по1МиБ+1/15/511B, затем точный GET и удаление.
Root не изменился. SMP test: HP1 проверил37047 xorshift заданий с0 ошибок;
одновременно шли8-МиБ SD PUT/GET с точным readback и RAM requests.
HP0 при этом обслуживал межъядерные и SD/timer IRQ, не теряя PIE данные.
HP1 pause/resume, stack guard80/8192, LP timer и background RTC/UI без ошибок.

Это фиксированный single-foreground owner, не поддержка миграции SIMD-задач
между ядрами. Для будущего SIMD из ISR/task switching нужен отдельный context ABI.
Артефакты, JSON и USB логи: игнорируемый `target/ethernet-pie/`.

## Результат

| Полный тракт, МиБ/с | A1 scalar | B PIE | A2 scalar |
|---|---:|---:|---:|
| RAM GET | 4.326 | 5.282 | 4.323 |
| RAM POST | 4.964 | 6.417 | 5.063 |
| SD PUT | 2.400 | 2.972 | 2.475 |
| SD GET | 3.438 | 4.011 | 3.442 |

RAM — медианы7 измеренных запросов на направление; SD — средние2 файлов
по32МиБ. Возврат A2 к уровню A1 подтверждает эффект: около+22% RAM GET,
+27–29% RAM POST,+20–24% SD PUT,+16–17% SD GET. Последний процент зависит
от того, с каким scalar-контролем сравнивать; не приписываем дрейф карты SIMD.

Пример целого RAM GET4МиБ: scalar925165us, TX copy187639us;
PIE751912us, TX copy23817us. RX copy POST также уменьшилось примерно со148ms
до26ms на4МиБ. Остальные стадии не исчезли, поэтому ускорение копирования
не превращается в такое же ускорение полного HTTP.

Во время B GET аппаратно скопировано0x421820 TX vector bytes, scalar tail/
короткие пакеты0x7612B; CPU pointers0x4ffb8e20/0x4ffb9420, оба alignment16.
POST аналогично использует SIMD RX. Таким образом это не замер scalar fallback.
Все6 основных32-МиБ файлов прошли полный readback и cleanup; исходные файлы
SD не изменялись. Размер B payload305436B против A303900B, разница1536B;
изменение памяти — код и небольшой owner/telemetry, без нового постоянного
packet scratch. Есть одинаковое выравнивание CPU frame fields в обеих сборках.

115 host tests, target Clippy для `ethernet-pie` и all-features проходят.
Feature остаётся опциональным, чтобы сохранять возможность воспроизвести A/B.

В совокупном стресс-тесте B EMAC missed-frame counter=35, у scalar A2
после тех же видов тестов=105. Точный порядок дополнительных сценариев
различался, поэтому это не количественный benchmark снижения потерь.
Факт важен: потери кадров под параллельной нагрузкой существуют в обоих
вариантах, TCP восстановил поток, все readback точные; rx_errors=0.
Нельзя на этом основании объявлять приём lossless или считать проблему
связанной только с PIE. Ring/FIFO/время обслуживания остаются отдельной
темой профилирования. После эксперимента на плате оставлен B; HP1 load=OFF.

На итоговом B дополнительно проверены stop/restart EMAC **без reset HP**:
закрытие web прошло Ok, арены вернули used=0, повторный claim HP0 PIE и
повторный startup self-test прошли. После restart RAM1МиБ GET/POST точные,
5.31/6.25МиБ/с. Первое readiness соединение ноут сам прервал по timeout во
время запуска, поэтому его единственный Err(Transport) ожидаем, следующий
запрос и последующие тесты прошли. Финально CPU≈159.99MHz, I0/I1 ON,
D OFF/L2=0, framebuffer guards=true, panel packet errors0; web оставлен online.
HP1 load=OFF, LP timer1000ms. В SMP-тесте HP1 выполнял integer xorshift:
одновременное применение PIE на обоих ядрах ещё отдельно не проверялось.
