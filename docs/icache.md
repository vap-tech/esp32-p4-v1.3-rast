# L1 I-cache при нулевом L2-cache, ESP32-P4 rev 1.3

Эксперимент 2026-11-06. Подтверждено на плате: core0 I-cache работает при
**L2 cache capacity=0**, L2 bypass, L1 D-cache bypass. Все 768 KiB L2MEM остаются
SRAM; внутренняя арена по-прежнему 496 KiB, stack 16 KiB. PSRAM остаётся uncached
через 0x88000000, LCD/SD DMA не требуют новой политики когерентности данных.
CPU1 не запускается. Частота CPU во всех проходах около 160 MHz, не меняется.

## Почему SRAM ускоряется кешем

TRM, раздел 9.3.1 (печатная стр. 902), различает CPU-доступ через кеш по
0x4… и прямой доступ по 0x8…. Для прямого доступа прямо указано, что он медленнее
доступа через кеш. Это относится и к внутренней HP L2MEM, а не только к PSRAM.
Раздел 9.3.2 (стр. 905–906) описывает HP L2MEM и перечисляет четыре конфигурации,
включая Config 3: 768 KiB L2 RAM / 0 KiB L2 cache. Раздел 9.3.3.2 (стр. 909–910)
описывает отдельный L1 instruction cache: 16 KiB, line 64 B, four-way.

Источник: [Espressif ESP32-P4 TRM](https://www.espressif.com/sites/default/files/documentation/esp32-p4_technical_reference_manual_en.pdf).
Локальная копия для исследования: target/memory-reference/trm.pdf и trm.txt;
нумерация глав/страниц относится именно к этой копии, новые редакции могут отличаться.

L2MEM — SRAM за подсистемой межсоединений, а L1 — отдельная небольшая память
около CPU. Попадание в I-cache позволяет повторно использовать инструкции без
каждого обращения к L2MEM. Поэтому «код уже в SRAM» не означает «кеш бесполезен».
TRM также описывает доступ к L2MEM на половине частоты HP CPU; точную стоимость
одной выборки и число тактов ожидания этим экспериментом не измеряли.

Счётчики и повторяемое изменение времени подтверждают влияние пути инструкций.
Эксперимент не измеряет отдельно latency банков SRAM, pipeline stalls или вклад
D-cache; также не доказывает, что все оставшиеся задержки вызваны памятью.
Это исследование cache/bus hierarchy, не микрокода CPU.

Структурное объяснение: SRAM — технология хранения, а не гарантия одинаковой
латентности на всех уровнях. L1 I-cache тоже использует быструю внутреннюю память,
но обслуживает небольшой горячий набор инструкций другим путём. Поэтому Espressif
описывает ожидаемое свойство архитектуры, а не программный ускоритель.

## Реализация и ограничения

`hal::memory::set_instruction_cache(bool)` исполняется целиком из SPM (проверен
дизассемблер, адрес 0x30101676). Перед переключением проверяет нулевой L2 и
bypass D-cache/L2. Временно bypass core0 I-cache, invalidate-all только его,
ожидание DONE с ограничением, затем выбор bypass и fence/fence.i. Core1 остаётся
в bypass. Режимы D-cache, L2, PMA и CPU clock не меняются.

Доступные команды:

```sh
# После reset показать JPEG и сравнить обе реализации без I-cache:
python3 scripts/display-control.py --icache off --image HOME.JPG --jpeg-idct-bench HOME.JPG
# Тот же бинарь, только I-cache включён:
python3 scripts/display-control.py --icache on --clock --memory --jpeg-idct-bench HOME.JPG
# Вернуться к прежнему экспериментальному режиму:
python3 scripts/display-control.py --icache off
```

Консоль: `:icache on` / `:icache off`. Это явный runtime-переключатель:
**после reset все кеши снова bypass**, обычная политика загрузки не изменена.
Полные memory-test/memory-bench пока требуют all-bypass: перед ними I-cache
нужно выключить. Инициализация верхней SRAM выполняется до включения I-cache.
Исполняемая SRAM после старта не изменяется; при будущем self-modifying code
или DMA-загрузке кода понадобится отдельный протокол синхронизации инструкций.
DMA-буферы остаются некешируемыми, текущие data fences достаточны при этой политике.

ESP-IDF v6.1 Kconfig.cache предлагает 128/256/512 KiB L2, без нулевого выбора.
Это ограничение штатной конфигурации SDK, не доказательство запрета аппаратного
режима. Не переносить на rev>=3 адреса размещения cache/RAM из этого эксперимента.

## Методика и результаты

Образ 135552 B, SHA256:
`74432d0da544c2d1396ea85b8f956e86bd8d5e2e45d7f6966d27ec75b37a2ed9`.
Один бинарь, runtime порядок **ON → OFF → ON**, внутри каждого режима LMML:
Loeffler, Matrix, Matrix, Loeffler. HOME.JPG с SD, 1024×600, 14592 блоков,
264 DC-only. LCD постоянно читает тот же framebuffer. Полный decode_us включает
SD, вычисления и запись; дополнительные операции total_us не смешиваем с decode.

| Метрика | I-cache OFF | I-cache ON (первый цикл) |
| --- | ---: | ---: |
| Matrix decode | 7.630467 s | 3.764172 s |
| Loeffler decode | 4.963978 s | 2.461742 s |
| Matrix IDCT | 4.482549 s | 2.026180 s |
| Loeffler IDCT | 1.818843 s | 0.725915 s |

Полное декодирование ускорилось примерно в **2.03 раза / 2.02 раза** только от
I-cache. Loeffler IDCT — примерно в **2.51 раза**.
Повторный ON после OFF дал Matrix 3.764573 s / Loeffler 2.462013 s;
разброс между двумя ON-циклами менее 0.02%. Старые числа 7.355/4.845 s
относятся к другой раскладке бинаря; для сравнения режимов используем эту таблицу.

Аппаратные счётчики включаются непосредственно вокруг jpeg_trial, без печати
внутри измерения. Порядок значений: hits, misses, conflicts, next-level reads.
Пример Matrix ON: `[315575415, 27114, 0, 3645]`.
Пример Matrix OFF: `[0, 1210195060, 0, 0]`.
Это сырые аппаратные единицы: нельзя интерпретировать miss count в bypass как
число загрузок физических cache lines или вычислять CPI из этих значений.
Малое число next-level reads и многочисленные hits при ON подтверждают работу L1.

В обоих режимах одинаковые контрольные суммы:

| Алгоритм | Pixel hash | Полный framebuffer hash |
| --- | --- | --- |
| Matrix | c3d5b982 | e5cb9e80 |
| Loeffler | 534b3012 | b3420c10 |

Все проходы: framebuffer guards=true, stack guard_ok=true, high_water=10956/16384 B.
SD выполняет только чтение. Камера и аудио не запускались.
Логи: target/icache-experiment/{on-final-first,off-final,on-final-second}.log.
37 host tests passed, 2 asset diagnostics ignored; clippy -D warnings,
Python syntax и git diff --check прошли.

D-cache-only и сочетание I+D при нулевом L2 ещё **не проверены**. Для них сначала
нужно реализовать data-cache maintenance для DMA либо выделить некешируемые
SRAM-буферы с соответствующими правилами адресов/владения. Сравнение с 128 KiB L2
потребует другой безопасной карты SRAM, поскольку верхняя арена сейчас занята.

## Продолжение: L2 и D-cache

[Контрольное исследование](cache-matrix.md) выполнено: 128 KiB L2 не обслуживают
этот SRAM JPEG, но положительный контроль PSRAM подтверждает работу L2.
При L2=0 оба L1 работают, Matrix 2.628 s / Loeffler 1.696 s. Прежнее предположение,
что L2 обязан обслуживать промахи I-cache к SRAM, неверно: путь внутренней памяти
идёт через L1. DMA и ограничения D-cache описаны в новом документе.
