# Организация памяти: resident kernel, данные и загружаемые модули

План развития от 2026-11-08. Первый этап уже реализован:
[SPM bootstrap и загрузка runtime в верхнюю SRAM](stage2-boot.md).
Динамическое вытеснение объектов, overlays, XIP и PSRAM execution пока не реализованы.

## Что есть сейчас

- 16 MiB Flash, 32 MiB PSRAM, 768 KiB HP SRAM/L2MEM при L2=0, отдельно 8 KiB SPM.
- Маленький bootstrap в SPM, code/rodata/data/BSS в upper SRAM. Fixed CODE 132 KiB
  удалён. Нижние 152 KiB выделены DMA pool, верхняя work arena начинается после
  всей статики и уменьшается по мере роста образа, runtime stack 16 KiB отдельно.
- Default unified image: около 163 KiB payload + 19.25 KiB BSS; свободно около
  314 KiB work + 152 KiB DMA. ROM-reserved 96 KiB не выделяются приложению.
- PSRAM CPU alias 0x88000000 некешируемый; это не готовый путь исполнения кода.
- Arena — bump allocation, память возвращается reset целого региона, не Drop.
  Независимые освобождения, movable handles и вытеснение пока не реализованы.

## Целевое разграничение

| Область | Что хранить | Жизненный цикл |
|---|---|---|
| SPM / resident SRAM | Boot/trap, управление памятью, обязательные HAL и код обслуживания активных устройств | Всегда резидентны |
| SRAM DMA pool | Дескрипторы и необходимые SRAM DMA buffers, изолированные cache lines | До подтверждённой остановки периферии |
| SRAM session arenas | TCP/SD окна, JPEG/DSP scratch, временные структуры активной задачи | Освобождение по завершении сессии |
| PSRAM bulk | Framebuffer, большие данные, файловые/сетевые очереди, холодное состояние | Явное владение, возможна выгрузка через handles |
| PSRAM code/cacheable data | Некритичный код и часто используемые внешние таблицы | Только после настройки и проверки отдельного пути исполнения/кеширования |
| Flash image/assets | Неизменяемые HTML.gz, таблицы, код модулей, ресурсы | Постоянно; чтение порциями, XIP либо загрузка |

Размеры областей выбирать по linker symbols и измеренным peak usage, а не
объявлять всю свободную память одним heap. Для session arenas нужны отдельные
владельцы/scopes, чтобы завершение одного запроса не сбрасывало чужие DMA buffers.
При отсутствии запросов большие рабочие окна не должны оставаться занятыми.

## Что можно переносить

Большие данные лучше сразу создавать в PSRAM, выделяя SRAM scratch на время
обработки. Например: сеть -> SRAM окно -> FAT32/SD; большой файл целиком не
нужен ни в SRAM, ни в PSRAM. Аудиокольцо остаётся активным независимо от этой
сессии, если звук продолжает играть; framebuffer уже находится в PSRAM.

Холодные изменяемые данные можно копировать между SRAM и PSRAM только после
завершения всех обращений и DMA. Обычные Rust references/raw pointers не
перенастраиваются автоматически: для перемещаемых объектов нужен handle/ID,
manager и временное заимствование resident view. Нельзя прозрачно переместить
активный стек, произвольную структуру с внутренними указателями или DMA buffer.
Неизменяемые данные, имеющие копию во Flash/SD, можно просто отбросить и позже
загрузить заново, не занимая PSRAM резервной копией.

## Код: три разных механизма

1. **Flash XIP:** постоянное отображение кода во Flash через MMU/кеши.
   SRAM не содержит полную копию такого кода; cache lines заполняются аппаратно.
   Нужны собственные настройка MSPI/MMU/cache и правила работы во время flash
   операций. Минимальную конфигурацию L1/L2 для нашей rev1.3 ещё проверить;
   результат JPEG из SRAM при L2=0 сам по себе не доказывает Flash XIP при L2=0.
2. **Исполнение из PSRAM:** P4 это поддерживает. Локальный IDF v6.1,
   `components/esp_psram/esp32p4/Kconfig.spiram`, содержит
   SPIRAM_FETCH_INSTRUCTIONS, SPIRAM_RODATA, SPIRAM_XIP_FROM_PSRAM;
   `components/esp_system/ld/esp32p4/memory.ld.in` использует executable
   PSRAM mapping 0x48000020. Это подтверждение возможности, не портированный
   драйвер. Нужны разделение физических диапазонов с нашим uncached bulk/DMA,
   PMA/MMU/cache и синхронизация при загрузке; не использовать два aliases
   одних данных без установленного протокола когерентности.
3. **SRAM overlays:** модуль хранится во Flash/PSRAM, копируется в выделенный
   executable slot SRAM, выполняется и выгружается. Начинать с фиксированного
   адреса слота и статически слинкованного модуля, а не general dynamic ELF loader.
   Нельзя просто memcpy произвольную функцию Rust: у неё есть адреса констант,
   переходы и зависимости. Нужны явная таблица вызовов resident kernel, ABI,
   формат/версия/границы модуля, I-cache invalidation и fence.i перед входом.
   Выгрузка разрешена только когда нет выполняющихся функций, return addresses,
   callbacks, IRQ handlers и ссылок на данные этого модуля. Несовместимые overlays
   не должны вызывать друг друга напрямую.

Для cold HTML/assets сначала достаточно Flash чтения в небольшой SRAM buffer:
исполнять их не нужно и заносить весь index.html.gz в resident .rodata незачем.
Это требует flash-read HAL/ROM wrapper и выделенного диапазона хранения,
но не требует исполнения кода из Flash или динамического линкера.

## Выполненный шаг: SRAM runtime loader

ROM image содержит только SPM bootstrap. После ROM-cache retirement и настройки
SRAM bootstrap читает runtime из фиксированного Flash manifest/payload, проверяет
геометрию и CRC, затем передаёт управление. Все обычные команды снова помещаются
в один образ, размерные features удалены. Исходники и карта — [stage2-boot.md](stage2-boot.md).
Это статически слинкованное приложение на весь сеанс; освобождения кода по задачам
или общего dynamic module loader пока нет.

Порядок развития:

1. Зафиксировать владельцев/границы и выводить бюджет CODE/rodata/static/DMA/
   session/stack/PSRAM раздельно, включая измеренные пики.
2. Убрать искусственное соревнование live buffers с холодными assets:
   assets во Flash/PSRAM, небольшие session windows в SRAM.
3. **Выполнено:** runtime загружается после настройки SRAM/L2; граница статики
   задаётся линкером, work arena начинается за ней, reset не затрагивает код.
4. Проверить Flash XIP и PSRAM execution отдельными небольшими образами,
   включая ROM reset, cold boot, I-cache/D-cache и активные SD/LCD/DMA.
5. Только если измерения это оправдают, добавить overlays для крупных
   взаимоисключающих модулей (диагностика, JPEG, инструменты форматирования).

Перемещать работающий TCP/SD/audio стек целиком ради одного запроса не требуется.
В первую очередь нужны правильное размещение и освобождение рабочих данных;
loader/overlays решают отдельную задачу размера resident executable кода.

Проверка 2026-11-08 уточнила шаг 3: прямой ROM-loaded probe подтвердился на
`4ff40000/4ff60000`, но не сохранился на `4ff80000/4ffb8000` после старта.
Чтение тех же 32 B из Flash через ROM уже после настройки L2=0 и исполнение
на двух последних адресах прошли. Следующий loader должен учитывать этот
порядок; общий boot destructive-test больше не является препятствием.
Подробности, границы доказанного и логи — [memory.md](memory.md#проверка-загрузки-верхней-sram-2026-11-08).
