# Аппаратный JPEG: экспериментальный драйвер

Первичный bring-up ESP32-P4 rev1.3, 2026-11-15.
Позднее HAL выделен в `hardware-jpeg`: его включает штатная
[фоторамка](photoframe.md), а лабораторные команды по-прежнему opt-in.
Далее — исходные результаты лаборатории.

Лабораторные команды включает опциональная feature `jpeg-lab`.
Сам HAL используется и фоторамкой. C/IDF runtime не добавлен.
HAL написан на Rust по TRM и локальным исходникам ESP-IDF v6.1:
`esp_driver_jpeg/jpeg_decode.c`, `jpeg_parse_marker.c`, `esp_hal_jpeg/jpeg_hal.c`,
`esp_hal_dma/esp32p4/include/hal/dma2d_ll.h` и `esp_driver_dma/src/dma2d.c`.

## Что работает

JPEG выполняет entropy decode, dequant и IDCT; 2D-DMA делает перестановку блоков,
аппаратный YCbCr→RGB565 и запись результата в PSRAM. CPU разбирает заголовок и
загружает таблицы. Поддержаны baseline sequential Huffman, 8-bit DQT, gray,
YCbCr 4:4:4 / 4:2:2 / 4:2:0. Размеры кратны 8, выход дополнен до MCU; progressive,
CMYK и multiscan отклоняются. DRI разбирается, но отдельный restart-корпус на
железе пока не проверен. Проверены только D-cache OFF, L2=0.

Основной путь: вход и выход — uncached PSRAM (`0x88…` у CPU, `0x48…` у DMA), дескрипторы — SRAM.
Нативный RGB565 little-endian. Есть явный выбор JPEG full-range либо BT.601
limited-range; лаборатория использует первый. Матрица из примера IDF растягивает
уровни как для видео и для нашего JPEG давала заметное отличие.

HAL требует исключительного владения JPEG и всей 2D-DMA; одновременная PPA
недопустима. Буферы удерживаются до завершения и опустошения write FIFO либо
подтверждённого abort. Если остановку подтвердить нельзя, panic вместо возврата
живой DMA-памяти аллокатору. Polling timeout 1 с; это диагностическая блокирующая
операция, без обслуживания HTTP/аудио/UI, не готовый фоновый сервис.

## Проверки на плате

Команда после остановки web через ESC:

```
:display jpeg hardware test
:display jpeg hardware HOME.JPG
:display jpeg hardware dump HOME.JPG
```

Скрипт: `python3 scripts/display-control.py --jpeg-hardware [PATH]`.
Не запускать второй serial reader одновременно с монитором.

Авторские JPEG fixtures в `tests/fixtures/hw-*.jpg` созданы ImageMagick:
серый квадрат 16×16 и цветовые полосы 32×16, три sampling mode. Проверяются
все пиксели (для серой полосы допустим один шаг RGB565 из-за округления), порядок байтов и canary вокруг входа, выхода и дескрипторов.
Дополнительно повреждённый entropy stream с ранним EOI должен завершиться
ошибкой/таймаутом; затем исправный JPEG должен декодироваться без перезагрузки.

HOME.JPG (114892 байта, 1024×600, 4:2:0) декодирован за 12979 мкс, включая
настройку таблиц и остановку DMA, но без SD, выделения памяти и checksum.
Выход 1024×608×2 = 1245184 байта, FNV-1a `8ad2b423`. Весь выход считан по USB,
проверен по checksum и восстановлен на ноутбуке. После обрезки до 600 строк
средняя абсолютная RGB8-ошибка относительно ImageMagick — 2,48, RMSE 3,48,
максимум 51 (битового совпадения с другим IDCT/chroma upsampling не ожидаем).
С прежней limited-range матрицей средняя ошибка была 7,36.

Дисплей продолжает читать прежний framebuffer, JPEG offscreen, scanout не
переключается. Защитные области целы, host errors LCD равны нулю. Артефакты
и raw dumps лежат в игнорируемом `target/jpeg-lab/`.

## AXI RID_ERR_CNT: воспроизводимый startup workaround

В первоначальном драйвере после decode RID_ERR_CNT был обычно4, иногда5–6,
при нулевых RRESP/WRESP. Перенос дескрипторов, owner-check и descriptor burst
причину не устраняли. Счётчик не был остатком write FIFO: после drain сохранялся.

Поэтапный запуск локализовал условие: начало RX (чтение его дескриптора)
при ещё незавершённых AXI-чтениях TX. Пауза50мкс после TX убирала ошибку;
та же пауза только после RX — нет. Простой prefill TX тоже недостаточен:
в AXI read/backup FIFO ещё оставались команды, и RID снова появлялся.

Рабочая последовательность без фиксированных задержек:

1. Опубликовать дескрипторы и стартовать TX.
2. Дождаться данных в TX L3 FIFO либо OUT_DONE для короткого потока.
3. Дождаться нуля AXI RD_FIFO_CNT и RD_BAK_FIFO_CNT (`AXI_ERR & 0x7f000`).
4. Стартовать RX, затем JPEG.
5. После RX EOF дождаться write drain, затем quiesce/reset до освобождения.

Ожидание старта ограничено100мс; при timeout выполняется общий abort и возврат
ошибки. Все три AXI error counter теперь фатальны, включая RID. Ошибки проверяются
также после write drain/abort, до reset не маскируются. Snapshot сохраняет
показания перед стартом и после TX/RX, до и после завершения.

Контроль A/B/A: без drain первый gray16 дал RID=3 и Hardware error; с drain
серия снова прошла. Две серии по500 декодирований gray/444/422/420 и SRAM420 (разные старты):
все пиксельные эталоны и canaries целы, RID/RRESP/WRESP=0. Источник только SRAM
и источник+выход SRAM также проверены: проблема не специфична для PSRAM alias.
Команда стресс-теста: `:display jpeg hardware stress`.

Это измеренный обход условия на нашем rev1.3, не доказательство конкретной
внутренней ошибки AXI-арбитра и не официальный erratum Espressif. Исходники
IDF стартуют TX→RX→JPEG отдельными вызовами и явно этот счётчик не проверяют;
само отсутствие ожидания в них не доказывает корректность нашего быстрого
регистрового старта. DMA-767 относится к AHB DMA rev3.0 и сюда не переносится.

Драйвер пока остаётся opt-in `jpeg-lab`: потоковая интеграция, совместное
планирование с PPA, энкодер, swap framebuffer и UI фоторамки не реализованы.

[Официальное описание JPEG](https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/peripherals/jpeg.html).
[Официальные errata](https://docs.espressif.com/projects/esp-chip-errata/en/latest/esp32p4/02-errata-summary/index.html).

Финальная серия gray/444/422/420 + SRAM + early-EOI timeout + повторный420 прошла;
119 host tests, target Clippy и форматирование прошли. На плату после проверки
возвращена стабильная Ethernet-PIE сборка, лабораторный JPEG не активен.

20 повторных HOME.JPG после исправления:12736–13582мкс, неизменный
FNV `8ad2b423`, все финальные AXI error counters нулевые.

После добавления PPA JPEG использует общий эксклюзивный `dma2d::Claim`;
контракт полного владения аппаратурой не изменился. [PPA FILL](ppa.md).
После перевода на общий Claim дополнительно прошли500 JPEG после PPA и три
HOME.JPG между сериями PPA; guard цел, checksum прежний, AXI errors=0.
