# Профиль HTTP upload64MiB — 2026-11-14

Плата P4 rev1.3, CPU160MHz, Ethernet100/full. I-cacheON, D-cacheOFF, L2=0,
uncached PSRAM, LCD активен. Очереди/размеры и алгоритм записи не менялись.
Диагностический образ включает замеры; штатный образ после опыта возвращён.
Исходный root до/после совпал, пользовательский большой AVI сохранён.

## Ethernet и TCP

Диагностический sampler периодически читает read-to-clear DMA+0x20 и накапливает
счётчики: RX buffer misses0, RX FIFO overflow0; флаги переполнения счётчиков0.
Максимальный интервал между входами в Network::tick —4632us. Профиль Emac:
1961579 receive calls,55243 принятых кадров,2374287us копирования RX;
24575 transmit calls,78266us копирования TX,48354us ожидания TX-descriptor.
Счётчики кадров не равны числу пакетов в Linux-захвате из-за offload.

tcpdump на проводном интерфейсе ноутбука, snaplen128B, фильтр только адреса борды
и TCP80.109837 пакетов, потерь захвата kernel0. В основном PUT TCP-потоке
нет повторных payload sequence ranges/перекрывающихся байтов. GET также без
перекрытий. Перестановки и повторения не выводятся из одного EMAC-счётчика —
здесь они дополнительно проверены по TCP sequence ranges.

Борда отправила12180 пакетов с рекламируемым window=0. По переходам между
нулевым и ненулевым окном это12180 интервалов,37,607s суммарно из49,446s.
Это наблюдаемое ноутбуком объявленное окно, не измерение внутренней физической
занятости RX-buffer. Данные удерживаются в TCP RX пока foreground копирует
PSRAM/ждёт файловую операцию, а новое окно объявляется последующим tick.
Были392 межпакетных паузы данных >20ms, максимум93ms; повторной передачи данных
в этих паузах нет. Это backpressure приложения, не доказательство плохого кабеля.

## Вывод и следующий кандидат

Прямой DMA-путь PSRAM → SD уже достаточно быстр для нынешнего сетевого канала.
Главная измеренная добавочная стоимость — мелкие записи метаданных FAT.
Затем идут CPU-копирование PSRAM и отсутствие перекрытия наполнения следующей
очереди с await текущего файлового запроса.

Первый кандидат: объединять изменения FAT в секторе/пакетно выделять кластеры
с учётом известного Content-Length. Требуется сохранить порядок dirty-marker,
FAT, directory-entry и sync, корректный abort и две FAT-копии. Это изменение
политики записи метаданных, а не увеличение32-КиБ буфера. В локальном IDF FatFs
`components/fatfs/src/ff.c` функции sync_window/move_window используют dirty
sector window: обновлённый сектор хранится до смены окна/синхронизации и затем
отражается во вторую FAT. Копировать C runtime для этого не требуется.

Следующий отдельный этап — наполнение другой PSRAM-очереди во время SD await,
с явным владением источником текущего DMA. По одному профилю обещать итоговую
скорость после этих изменений нельзя; удаление21,27s само по себе даёт лишь
теоретические64/(49,45−21,27)≈2,27MiB/s при неизменных остальных интервалах.

## Артефакты и ограничения инструмента

Все замеры gated diagnostics. SD PROFILE теперь имеет26 полей: прежние24
сохранены по индексам, добавлены24=metadata_ready_us и25=payload_ready_us.
HTTP NET выводит poll/max-gap, EMAC profile и четыре накопительных loss counters.
shared=true предупреждает о других файловых передачах внутри глобальных счётчиков.

Первый запуск остановился до открытия файла из-за двух заимствований одного
RefCell в аргументах snapshot; снимки разделены на отдельные statements.
После исправления прошли smoke PUT/GET/DELETE и основной64MiB тест.
Stack56420/65536B, guard_ok=true; штатное завершение web-run Ok, memory pool
очереди:1 блок32KiB+guards. Исходные файлы не изменялись.

Артефакты в target/storage-profile: http64-profile.pcap, http64-packets.json,
http64-stages.json, p4-http-profile-web.log, p4-http-profile64.json и скрипт
p4-profile-pcap.py. Логи не входят в git; этот документ фиксирует результаты.
