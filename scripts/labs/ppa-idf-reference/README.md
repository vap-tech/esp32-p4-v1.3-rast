# Отдельный контроль PPA BLEND на IDF

Диагностическое C-приложение для ESP32-P4 rev1.3, ESP-IDF v6.1
`fff9895c82d744c7237be8847347bdd1b07c6643`. Не входит в Rust-прошивку.
SDK не патчится. Результаты и ограничения: [docs/ppa-blend.md](../../../docs/ppa-blend.md).

После активации отдельного IDF environment, из корня репозитория:

```sh
idf.py -C scripts/labs/ppa-idf-reference -B target/ppa-idf-reference \
  -D SDKCONFIG="$PWD/target/ppa-idf-reference/sdkconfig" build
```

Сборка по умолчанию использует только SRAM. Через menuconfig можно включить
PSRAM: HEX,200МГц, boot init, caps allocator, memory protection. Код выберет
SPIRAM вместо INTERNAL; явный cache-msync сохраняется в обоих режимах.
Используются штатные PPA/DMA2D драйверы, USB Serial/JTAG driver и VFS.
Ранние SDK-логи отключены, stdout unbuffered, ручного fflush нет.

При последующих вызовах menuconfig/flash использовать те же -C/-B/-D.

Прошивка **заменяет загрузчик и приложение**; перед её запуском нужен готовый
образ возврата Rust. Автоматически ничего не шьётся. Если запускать `idf.py
flash`, сначала остановить serial monitor; затем открыть USB-консоль115200.
Стенд не использует SD, LCD, Ethernet или Wi-Fi. После трёх проходов остаётся
в ожидании, чтобы не выключать DMA2D до чтения диагностических регистров.

Для каждой операции печатаются результат API, `axi_err` до/после, число
ошибочных пикселей и повреждённых guard-байтов. Промежуточная альфа допускает
один native шаг RGB565 на канал, endpoints и область вне ROI проверяются
точно. `ESP_OK` и правильные пиксели при ненулевом RID не означают, что
аппаратную ошибку можно игнорировать. RID —4-битный счётчик с rollover;
сравнение только конечных значений не считает все ошибки за операцию.

SDKconfig и build artifacts хранить под `target/`, либо в отдельной копии
этого стенда. Основной пользовательский checkout SDK менять не требуется.
